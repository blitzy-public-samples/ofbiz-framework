== Building and running OFBiz using Docker

OFBiz includes a Dockerfile which can be used to build a container image
for running OFBiz. The container image is built based on the sources
already available in the build content, i.e. it only uses sources that
you have already downloaded.

If you want to include any plugins in your container image, you must
download those plugins before running the build. (See the plugin
documentation in `+README.md+`).

=== Quickstart

Follow these instructions to get started building and running OFBiz
using Docker.

==== Build the OFBiz container image

From the sources directory (i.e. the directory containing this
`+DOCKER.adoc+` file), first make sure the `+plugins/+` git submodule is
populated - the build reads the sources already in the working tree, so an
uninitialised submodule silently produces an image with no plugins:

[source,shell script]
git submodule update --init

Then build the image:

[source,shell script]
docker build --tag ofbiz-docker .

==== Run the OFBiz container

Run the following command:
[source,shell script]
docker run -it -e OFBIZ_PROFILE=dev -e OFBIZ_DATA_LOAD=demo --name ofbiz-docker -p 8443:8443 ofbiz-docker

This will start an instance of the ofbiz-docker container, publish port
8443 to localhost, load the OFBiz demo data, and then run the OFBiz
server.

`+OFBIZ_PROFILE=dev+` is the profile for a local container like this one:
it generates the signing keys it needs and keeps the published demo admin
password. It is also what an unset `+OFBIZ_PROFILE+` resolves to, so
`+docker run ofbiz-docker+` with no environment variables at all still
boots on the embedded database; the container reports the assumed profile
as a `+NOTICE+` on start up. Use `+OFBIZ_PROFILE=prod+` for anything
serving real traffic, which is never assumed and which requires every
secret to be supplied - see _Secrets_ below.

Once start up completes, you can access OFBIZ at
https://localhost:8443/partymgr

=== Other container building options

The OFBiz `+Dockerfile+` defines a multi-stage build. The default
container image produced by the build is named `+runtime+` and consists
of an uninitialized OFBiz installation.

During the first run of a container based on the runtime image, seed or demo
data can be loaded and an admin user created.

The runtime container is the default target of a docker build and can be
created with commands similar to the following, once
`+git submodule update --init+` has populated `+plugins/+`:
[source,shell script]
docker build --tag ofbiz-docker .

or
[source,shell script]
docker build --target runtime --tag ofbiz-docker .

The Dockerfile also defines another stage, `+demo+`, which produces a
container image with demonstration data already loaded. This container
image may be useful in cases where containers are frequently run and
destroyed and the time taken to load demo data is becoming noticeable.

To build a container image pre-loaded with demo data, run:
[source,shell script]
docker build --target demo --tag ofbiz-docker .

=== Container runtime options

The container’s behaviour at runtime is controlled via environment
variables, '`hook`' scripts and XML entity import files.

Two kinds of work are distinguished, and they behave differently.
*Configuration rendering* - the database settings, the signing keys, the
admin key, the content URL prefix, the object store and the load balancer
settings - is redone on *every* start, from the pristine copies shipped in
the distribution. A rotated secret, a changed database host or a newly
enabled feature therefore takes effect when the container is restarted, and
a variable that is *withdrawn* takes effect too: its override is removed
rather than left behind stale. *Data initialization* - loading the seed or
demo data, loading the admin user, running the hooks and disabling
components - is done once, during the first run, and markers stored in
`+/ofbiz/runtime/container_state+` record that it was done so that a
subsequent start skips it.

Those markers are not bare flag files. Each one records the settings it
was written for and a checksum of that record, and is believed only when
both still match the container being started. A marker left on a reused
volume, one that was written for a different database, a partially
written one, a hand-edited one and one written by a different image
version are all disbelieved, and the work they claim to have done is
performed again - every step behind a marker is safe to repeat. A marker
can therefore never be used to make a container skip work it has not
actually had done for the database it is now pointing at.

`+OFBIZ_SKIP_INIT+` moves that boundary in one direction only: it skips the
data initialization, and it skips nothing else. It cannot skip the
configuration rendering, and it never could, because `+/ofbiz/config+` is a
volume that outlives the container - so whatever it is set to, the profile is
validated, the startup-DDL posture of the entity configuration, the
object-storage provider and the cache-invalidation transport are validated,
and their overrides are rendered or removed, on every start.

Use of environment variables, hook scripts and XML entity import files
are managed by the `+docker-entrypoint.sh+` script.

==== Environment variables

Environment variables are used in `+docker-entrypoint.sh+` to control
configuration options for the OFBiz container.

Every variable documented below as a boolean accepts `+true+`, `+yes+` or
`+1+` and `+false+`, `+no+` or `+0+`, in any letter case. The value is
normalised before anything is written, so a rendered configuration file only
ever receives the literal `+true+` or `+false+` - which is all the OFBiz
side recognises - and any other value aborts the start up rather than being
guessed at.

How a variable reaches OFBiz is the same for nearly all of them.
`+docker-entrypoint.sh+` renders environment-substituted copies of the
configuration it owns - `+entityengine.xml+`, `+security.properties+`,
`+org/apache/ofbiz/base/start/start.properties+`, `+url.properties+`,
`+content.properties+` and the three cache-invalidation transport files -
into `+/ofbiz/config+`, starting from the pristine copies shipped in the
distribution. That directory precedes `+ofbiz.jar+` on the class path, so
the rendered copy is the one OFBiz reads and no file inside the
distribution archive has to be rewritten. Three properties of that
arrangement are worth knowing before reading the tables:

* it is redone on *every* start, so a value that is *withdrawn* is
  withdrawn: the override is removed, or re-rendered with the committed
  value, rather than left behind. `+/ofbiz/config+` is therefore the entry
  point's own working directory for the files it renders rather than a
  place to leave a hand-written one. The cache-invalidation transport is
  the one exception: those three files may be supplied by an operator
  instead, because only a file carrying the entry point's
  `+GENERATED BY docker-entrypoint.sh+` marker is replaced or removed -
  see _Running more than one instance_ below;
* every override that carries a credential is written atomically, owned
  by the `+ofbiz+` user and mode `+0600+`, and its value is substituted
  from a temporary file rather than from a command line;
* every variable that carries a credential is then *removed from the
  environment* before OFBiz - or any hook, or any initialisation JVM - is
  started, so the server process does not hold it. See _Secrets_ below.

The settings of the embedded servlet container are the exception, because
`+framework/catalina/ofbiz-component.xml+` is a component descriptor
rather than a class-path resource and `+/ofbiz/config+` cannot shadow it:
`+OFBIZ_JVM_ROUTE+`, `+OFBIZ_SSL_ACCELERATOR_PORT+`,
`+OFBIZ_ENABLE_CROSS_SUBDOMAIN_SESSIONS+` and `+OFBIZ_ENABLE_AJP_PORT+`
are applied to that descriptor in the unpacked installation instead. They
too are applied on every start, from the value supplied or from the
committed default, so withdrawing one of them restores the committed
setting exactly as removing an override does.

The table below lists the variables that are not specific to one
subsystem. Variables that configure a single subsystem are listed and
explained in that subsystem's own section further down - the database
connection under _PostgreSQL_, the credentials under _Secrets_, the
object store under _Content and upload storage_, the probes under
_Health and readiness endpoints_ and the fleet settings under _Running
more than one instance_ - so that every variable has exactly one
authoritative description.

The *Default value* column gives the value that ends up in force when the
variable is not supplied - the *effective* default, not merely the empty
environment. Where the two differ, because the entry point restores a value
committed in the distribution rather than writing nothing, the column names
the committed value and the description says where it comes from. A default
shown as _empty_ or _unset_ means the resulting configuration really does
carry no value for that setting.

===== Load balancers and TLS-terminating proxies

Setting `+OFBIZ_SSL_ACCELERATOR_PORT+` installs
`+SslAcceleratorValve+`, which marks every request arriving on that
local port as secure so OFBiz rebuilds absolute URLs as `+https+`. The
valve grants those TLS semantics on the strength of the local port
alone: it verifies no source address, no `+X-Forwarded-Proto+` and no
`+Forwarded+` header. *The port number is not the trust decision - the
network is.*

Enable it only when the forwarded-traffic connector is unreachable
except through the proxy. Bind it to a private interface - uncomment and
set the `+http-connector+` `+address+` property in
`+framework/catalina/ofbiz-component.xml+`, or publish only the
balancer-facing address - and restrict it in the network layer with a
security group, firewall rule or private subnet that admits the proxy
alone. Do not enable it on a connector bound to `+0.0.0.0+` on a
routable interface: any client that reaches the instance directly would
then get a request that OFBiz treats as HTTPS, so cookies marked secure
are accepted over clear text and `+https+`-only request maps become
reachable over an unencrypted hop.

The proxy owns the other half of the boundary. It must strip client
supplied `+X-Forwarded-*+` and `+Forwarded+` headers and set them
itself, so a client cannot forge the forwarded protocol or address.
Where those forwarded values have to be honoured inside Tomcat, the
`+RemoteIpValve+` contract is what does it safely -
`+internalProxies+`/`+trustedProxies+` pinned to the proxy's own
addresses plus an explicit `+protocolHeader+`. That valve is not
installed by `+CatalinaContainer+`, so with this configuration surface
the equivalent guarantee has to come from the network restriction and
header hygiene above.

The value is validated before it is written: it must be a plain integer
between 1 and 65535 *and* match a port the *production*
`+catalina-container+` element of
`+framework/catalina/ofbiz-component.xml+` will actually listen on - 8080
for the http connector, 8009 for ajp, with no port offset in play. Only
that element is consulted. The same descriptor declares a second container,
`+catalina-container-test+`, whose connector ports no serving connector
listens on, and a value matching only one of those - 8010, its AJP
connector - is refused as well: the valve would be installed against a port
nothing receives traffic on, so it would never fire, every forwarded
request would keep its plain `+http+` scheme, and the symptom - redirect
loops or mixed content behind the proxy - would show up far from the
setting that caused it. Supplying the balancer's public HTTPS port, say
443, is refused for the same reason, and an unparseable value is refused
here instead of aborting container loading with a
`+NumberFormatException+`.

*With `+--portoffset+`, supply the offset port.* OFBiz binds every
connector at its declared port plus the offset the startup command asks for,
while `+SslAcceleratorValve+` compares the local port of the request against
this value with no offset of its own. So `+bin/ofbiz --portoffset=100+`
listens on 8180, not 8080, and 8180 is both the only value the valve can
ever match and the port the proxy or target group is pointed at. The start
up reads the offset from the command it is about to run, validates this
value against the offset ports, and names those ports - and the offset - in
the refusal if it does not match. With no offset, which is the ordinary
case, the declared ports and the bound ports are the same numbers.

The edits applied to the descriptor identify the production element by
position, so a descriptor that declares it more than once, or that declares
the test container before it, is refused outright rather than falling back
to searching the whole file. Each of the three properties must be declared
*exactly once* inside that element as well: `+ContainerConfig+` keeps the
last declaration of a property, so a duplicate - a patch applied twice, a
hook's edit, a hand edit on the writable layer - would let the container run
on a value the start up never checked. That is refused rather than
reconciled, because with two declarations there is no value the start up can
honestly report.

===== Health and readiness endpoints

Point the load balancer's target-group health check at one of the two
endpoints the webtools webapp serves. They are registered in
`+framework/webtools/webapp/webtools/WEB-INF/web.xml+` and need no
configuration:

[width="100%",cols="17%,17%,66%",options="header",]
|===
|Path |Method |Meaning

|`+/webtools/health/live+`
|`+GET+`, `+HEAD+`
|Liveness. Always `+200+` once the servlet container is up. It performs
no database access at all, so it keeps answering while the datasource is
unavailable. Use it to decide whether an instance has to be restarted or
replaced.

|`+/webtools/health/ready+`
|`+GET+`, `+HEAD+`
|Readiness. `+200+` when this instance can reach its datasource, `+503+`
otherwise. Use it to decide whether to route traffic to an instance. This
is the one to attach to the target group, so an instance is drained
rather than restarted when its database becomes unreachable.
|===

Both answer without a credential, so a probe is one request. Against a
container publishing 8443 on the local host, with `+-k+` because the
shipped certificate is self-signed:

[source,shell script]
----
curl -k -i https://localhost:8443/webtools/health/live
# HTTP/1.1 200 -- {"status":"UP"}

curl -k -i https://localhost:8443/webtools/health/ready
# HTTP/1.1 200 -- {"status":"UP","database":"UP"}, or
# HTTP/1.1 503 -- {"status":"DOWN"}
----

Copy those two paths into the target group exactly as they are written
here, and configure the check to expect `+200+`.

Readiness has exactly one dimension:

*Datasource* - the entity engine can execute one bounded query against
`+SequenceValueItem+` and get an answer. The query is a count under the
predicate `+1=0+`, so it can match no row: *any* successful execution is
the verdict, and nothing about the number it returns is examined. That is
deliberate on both counts. Naming no column means the probe holds no
opinion about the entity's fields, so no schema change can take a whole
fleet out of a target group; matching no row means the query is constant
work whatever the table holds, so readiness cannot become slower as a
deployment grows. The entity is still in the `+FROM+` clause, so the useful
half of a heavier check survives: a database with *no schema applied*
fails on a relation that does not exist and is correctly reported not
ready. Two situations therefore fail the dimension, and both are
`+HEALTH-READINESS-DATASOURCE-UNAVAILABLE+`: the database cannot be
reached at all - no delegator, an unreachable server, an exhausted
connection pool - or the schema has not been applied to it. *How much data
the database holds is not a readiness question*: a fleet loaded with
`+OFBIZ_DATA_LOAD=seed+`, or with `+none+` against an already-populated
database, is routable, and readiness never asks a probe to wait for a
sequenced write. See _Readiness and the contents of the database_ below.

*Readiness deliberately checks nothing else.* In particular it does not
inspect the cache transport, whatever `+OFBIZ_DISTRIBUTED_CACHE_CLEAR+` is
set to, and it does not contact the object store, whatever
`+OFBIZ_CONTENT_STORE_PROVIDER+` selects; it reads no content.

That is a decision about what a `+503+` ought to mean rather than an
omission, and one rule decides it: *a dependency the whole fleet shares is
not a readiness dimension.* A dimension over one is not a per-instance
verdict at all - it fails on every instance at the same moment and empties
the target group, withdrawing an application that is still serving correctly
and turning a degraded deployment into an unreachable one. The datasource is
the one dependency for which that is the right outcome, because an instance
that cannot reach it can serve almost nothing.

Both excluded dependencies fail that test, and both are real conditions
worth watching elsewhere:

* the *object store* is reached by a handful of operations, so an instance
whose datasource is healthy serves almost all of the application with the
bucket unreachable. It stays routable, and the store is monitored where it
lives;
* the *cache transport* is one broker serving the whole fleet, so a
dimension asserting a live subscription would empty the target group for a
fault that leaves every page correct - and would turn stale caches into an
outage. There is a second reason it is not asked: a subscriber's connection
state is not observable in a way a probe could trust - the listener's flag
carries no publication guarantee a reading thread can establish, so a probe
could report a disconnected instance as ready indefinitely, which is a worse
answer than not asking. Its *configuration* is enforced instead, at start up,
where it can still be corrected: an instance whose delegator enables
distributed cache clear without a transport configured for it does not start.
So watch the broker at the broker, and watch for an instance reporting that it
could not invalidate; do not let either decide routing.

The same rule keeps the other dependencies a deployment may acquire out of
the dimension list: an SMTP relay and an external OIDC provider are not
readiness dimensions either.

*So a probe cannot tell you whether content is being served - and neither
can a status code.* Monitor content separately, and assert on what comes
back rather than on the status when you do: a content read that fails is
answered with the application's own error page, which is a normal HTTP
`+200+` response, because the request did reach a working instance and
was handled, which is all a status code claims. A synthetic check that
fetches a known image and asserts on its length, its bytes or its
`+Content-Type+` reports a store that has stopped answering; one that
asserts `+200+` alone reports nothing. See _How content reaches and
leaves the object store_ below for which operations reach the store.

Both endpoints answer with a small fixed JSON document
(`+{"status":"UP"}+`, `+{"status":"UP","database":"UP"}+`,
`+{"status":"DOWN"}+`) marked `+no-store+`, and both are unauthenticated,
because a target group polls them without credentials. The `+503+`
document deliberately names no dimension: it would be a false statement
about the datasource whenever the coherence dimension is what failed.
Read the event codes below to tell the two apart, and keep any target-group
check asserting on the status code rather than on which members the body
carries.

Being unauthenticated makes them the most exposed surface of the
deployment, so they are deliberately narrow, and a probe configuration
that steps outside that shape gets a clear rejection rather than being
served:

* only `+GET+` and `+HEAD+` are answered. Everything else is `+405+`.
  `+OPTIONS+`, `+POST+`, `+PUT+`, `+PATCH+` and `+DELETE+` are refused by
  the endpoint itself, which answers `+405+` with an
  `+Allow: GET, HEAD+` header and a `+{"status":"DOWN"}+` body. `+TRACE+`
  is the one exception worth knowing about when writing a monitoring
  check: Tomcat's connector refuses it before any filter runs, because
  `+allowTrace+` defaults to `+false+`, so the observed answer is `+405+`
  with the connector's own `+Allow: OPTIONS+` header and an HTML body.
  The endpoint would refuse `+TRACE+` as well if a connector were ever
  configured to pass it through, so assert on the `+405+` rather than on
  the `+Allow+` value if a probe exercises `+TRACE+`;
* a request that announces an entity body - a `+Content-Length+` above
  zero or a chunked `+Transfer-Encoding+` - is `+400+`, decided from the
  headers alone, so *the endpoint itself* reads no part of that body. What
  runs in front of it is the webapp's ordinary filter chain, unchanged: the
  probes are registered as a servlet and allowed through
  `+ControlFilter+`'s allow-list, and no filter is added or modified for
  them. So a probe carrying a body is handled by those filters exactly as any
  other request with a body would be - `+ControlFilter+` builds a parameter
  map, which reads a form-encoded body, and `+ContextFilter+` turns a
  declared `+application/json+` body into request attributes - before the
  endpoint refuses it. A probe has no reason to send a body, and what bounds
  one if something does is the balancer's own cap and the connector's limits,
  both covered below. Nothing in a probe's own answer depends on the body
  either way;
* only these two exact paths are served. The integration is two edits to the
  webtools descriptor and nothing else: one `+servlet+` with one
  `+servlet-mapping+` carrying those two exact `+url-pattern+` values, and
  those same two exact paths appended to `+ControlFilter+`'s
  `+allowedPaths+`, beside the `+/ping.txt+` entry that was already there.
  No filter is added, and no framework filter is modified: the chain and its
  ordering are exactly what every other webapp has, which is what keeps this
  integration to the two descriptor surfaces and lets any webapp register the
  same servlet the same way.
+
The `+url-pattern+` values are *exact* rather than `+/health/*+`, and that is
what handles a near miss. `+ControlFilter+` matches `+allowedPaths+` with
`+startsWith+`, so `+/health/live+` in that list also admits
`+/webtools/health/live/+`, `+/webtools/health/livez+` and
`+/webtools/health/liveXYZ+` past the filter - but none of them matches a
mapping, so the container answers `+404+` and no application code runs. A
spelling that does not start with either entry - `+/webtools/health+`,
`+/webtools/healthz/live+`, or `+/webtools/HEALTH/live+`, the match being
case-sensitive - is not allowed through at all and is redirected exactly as
any other unauthenticated path is. Either way a typo in a target-group
configuration fails the check rather than passing it, but configure the check
to expect `+200+` *and* the JSON body rather than merely "not `+5xx+`", so
that a redirect cannot be read as health. Copy the two paths above into the
target group verbatim;
* the probe handler itself holds no state and reads none: no cookie, no
  principal, no role, no parameter and no attribute, and it never reads the
  request body;
* *a probe leaves no session behind*, which matters because the chain in
  front of it makes one. `+ControlFilter+` calls `+getSession()+`
  unconditionally - before it even consults its own allow-list - and
  `+ContextFilter+` does the same, so a session IS created for a probe, as it
  is for any request. The endpoint discards it: before writing anything it
  asks for the session, and if the session is one *this request* created
  (`+isNew()+`) it invalidates it and re-emits the response's `+Set-Cookie+`
  headers without the session cookie, expiring that cookie if it was the only
  one. So a probed instance accumulates no empty sessions, and a
  cookie-sticky load balancer cannot pin traffic with a cookie a probe was
  handed. A probe that arrives *carrying* somebody's session cookie - which a
  browser or a misdirected client can do - leaves that session alone, because
  invalidating a session that was not made for this request would log its
  owner out. The remaining two filters need nothing: `+CacheFilter+` computes
  a path and delegates, and `+SameSiteFilter+` rewrites `+Set-Cookie+`
  headers after the chain. Poll the endpoints as often as a target group
  requires;
* every answer, a rejection included, still carries the framework's safe
  response headers - `+X-Content-Type-Options: nosniff+`,
  `+X-Frame-Options: sameorigin+` and
  `+Referrer-Policy: no-referrer-when-downgrade+` - even though the
  probes are mapped outside `+/control/*+`, so the ordinary request
  handler that normally applies them never runs.
  `+Strict-Transport-Security+` and `+Content-Security-Policy+` are
  deliberately not emitted here: they are resolved through the entity
  engine, which a probe must not depend on, and they carry no meaning on
  a plaintext poll inside the load balancer's own network.

Two limits belong to the layers above the application, and since nothing
inside the application reads a body sent to a probe path, they are the only
things that bound one. Cap the request body the load balancer will forward
to a probe path, and keep the Tomcat connector's `+maxPostSize+`,
`+maxSwallowSize+` and `+maxHttpHeaderSize+` at or below their defaults
(2MB, 2MB and 8KB) - the connector is what reads or discards the body of a
request the application refused. The first and the last are listed,
commented out at exactly those defaults, among the connector properties in
`+framework/catalina/ofbiz-component.xml+`; `+maxSwallowSize+` is not
listed there and takes Tomcat's own default.

Exactly one readiness check queries the datasource at a time, and its
verdict is shared with every probe that overlaps it. A verdict answers
further probes on its own for one second after the datasource was
observed, and a probe that arrives while a check is running repeats the
verdict that check has not refuted yet, for up to five seconds. Probe
concurrency therefore never manufactures a `+DOWN+` answer for a
healthy datasource: an overlapping probe is answered from the check in
flight or from the verdict that still stands, never from a rejection.

Sharing the verdict is also what keeps the endpoint bounded. A readiness
query borrows a pooled connection, and when the pool is exhausted that
borrow blocks for up to the datasource's `+pool-sleeptime+` -
`+OFBIZ_DB_POOL_WAIT+`, 20000 milliseconds by default, on the managed
datasources and 300000 milliseconds on the embedded H2 ones - so an
endpoint that let every probe query would park one container thread per
probe for that whole wait and starve real traffic while answering nothing
but "are you ready". Only the probe running the check holds a connection;
the rest hold none. A probe with no verdict to fall back on - a JVM's
first probes, or a probe arriving once a check has been running longer
than the five seconds above - waits at most 500 milliseconds for the
check in flight, and answers `+503+` under
`+HEALTH-READINESS-PROBE-SHED+` only if that wait yields nothing either.

The check itself is bounded too, independently of the pool. It runs on a
single daemon thread and the probe that started it waits at most 2000
milliseconds for it, then answers from a verdict that has not been refuted
yet, or `+503+` under `+HEALTH-READINESS-CHECK-TIMEOUT+` when there is
none. What is bounded is *the probe*, not the check: a check that outruns
the deadline keeps running, keeps its permit and publishes the reading it
eventually gets, so no fresh check is started while it is outstanding and
no wedged datasource can accumulate one check per probe. That is the
behaviour to expect from the logs during a stalled datasource - one check
in flight, `+...-CHECK-TIMEOUT+` once a minute from the probe that owns it,
and `+...-PROBE-SHED+` from the others - and it is what recovers by itself
the moment the datasource answers. Without the bound a datasource that
accepts a borrow but never
answers - a wedged server, a lost packet on an established connection -
would leave the probe that started the check parked on it for as long as
the driver's own `+socketTimeout+` allows. Override the wait with the JVM
system property
`+ofbiz.health.readiness.deadline.millis+` when the target group's own
timeout demands it; it accepts 100 to 10000 milliseconds and any other
value is ignored with a warning in favour of the default.

The number of probes that may be in that wait *at the same time* is capped
at 32, which is what bounds thread occupancy rather than merely database
work. Coalescing the query means at most one probe touches the datasource,
but on its own it would still let an unlimited number of probes sit in the
500 millisecond wait, so a flood of a few thousand concurrent requests to
`+/webtools/health/ready+` could hold every connector thread without issuing
a single query. Beyond the 32nd waiter a probe is answered immediately, in
constant time, with no wait and no datasource access: from the shared
verdict when one exists, and `+503+` under
`+HEALTH-READINESS-WAITERS-FULL+` only when no verdict exists to answer
with. Tomcat's `+maxThreads+` defaults to 200, so a full waiter set is
around a sixth of the pool for half a second and leaves the great majority
of request threads for real traffic, whatever rate probes arrive at.

The cap is not a rate limit, and the number is chosen so that reaching it
cannot drain a healthy instance. An instance that has completed a check
within the five seconds above is answered from that verdict however many
probes arrive at once, so the cap is invisible to it. The cap is visible
only to a probe that finds no verdict at all - a JVM's first probes, and
the brief interval between a verdict ageing out and the next check
publishing - and only to the probes *beyond* the 32nd of such a burst.
Size it against the number of probes that can arrive *at the same instant*,
which is the sum of every prober pointed at the instance: each health-check
node a load balancer runs, each replica of any external monitor, and the
container orchestrator's own liveness and readiness probes. Ordinary
polling from a handful of probers is comfortably inside the cap - a cold
start is answered in full by the one check they all share - and the cap
starts to matter only once that instantaneous total approaches a few dozen.
Count your own probers rather than assuming a number, then point as many
target groups and monitors at the endpoint as the deployment needs; a
number of *simultaneous* probes in the dozens is what it takes to reach the
cap, and that is a flood rather than polling.

Probes are also exempt from the cross-subdomain session valve. With
`+OFBIZ_ENABLE_CROSS_SUBDOMAIN_SESSIONS=true+` that valve runs at Tomcat
engine scope - before any webapp's filters - and calls
`+request.getSession(true)+` on every request it sees. It recognises the two
probe paths and passes them straight through untouched, so switching the
valve on does not change what a probe costs. It is the outer of the two
things that together leave a probe with no session: this exemption at engine
scope, and the endpoint's own discard of a session the webapp's chain minted
for it, described above. It also covers the case the endpoint cannot - a
probe path addressed to a context that neither maps nor allow-lists it, by a
mis-pointed target group or a proxy rewriting the prefix - so no session is
minted at engine scope for a request that is going to be refused anyway, and
no domain-widened `+JSESSIONID+` cookie is written onto a response a probe
client never reads. Nothing is lost by the exemption: a
probe has no session to share across sub-domains in the first place.

Readiness stays a live signal despite the sharing, because a verdict is
never honoured for longer than the second above: a datasource that fails
is reported not ready, and one that recovers is reported ready again,
within about a second and with no restart. Configuring the check
therefore needs no special care - point as many target groups and
external monitors at `+/webtools/health/ready+` as the deployment needs,
at any interval, since they share one check instead of competing for the
datasource. `+/webtools/health/live+` performs no database access at all
and can likewise be polled at any rate.

A readiness failure is logged once per minute per instance as a stable
event code, with the occurrences suppressed in between counted into the
next line. A count still outstanding when the condition stops is written
out by the next readiness probe once that minute has elapsed, so the
tail of a burst - and a burst that ends inside its own minute - is
accounted for rather than lost. There are four codes, each with its own
once-a-minute limit and its own suppressed count, so no code can silence
another or report another's occurrences as its own:

* `+HEALTH-READINESS-DATASOURCE-UNAVAILABLE+` - the datasource could not
  be reached, or the bounded query did not complete, or the schema it
  names has not been applied. The database needs attention;
* `+HEALTH-READINESS-CHECK-TIMEOUT+` - a readiness check was started but
  did not publish a verdict within the deadline above. It reports a
  datasource that accepts work and does not finish it, which is a
  different fault from one that refuses a connection;
* `+HEALTH-READINESS-PROBE-SHED+` - no verdict could be obtained at all:
  a readiness check was running, it published nothing within the wait
  above, and no earlier verdict was recent enough to repeat. It reports
  a check that is not completing, so look at what the datasource is
  doing rather than at the probe configuration. A probe that repeats a
  verdict is a normal answer and logs nothing;
* `+HEALTH-READINESS-WAITERS-FULL+` - the 32-waiter cap was reached and the
  probe that hit it found no verdict to answer with either. It reports two
  things at once, so check both: what is sending that many simultaneous
  probes, and why a readiness check has not completed. A probe answered
  from the shared verdict after hitting the cap is a normal answer and logs
  nothing.

Keeping the four apart is what lets an alert tell those four
situations apart without parsing any log text. Nothing else is written:
no exception, no stack trace, no SQL, no connection string and no row
count reaches the log from a probe, at any log level, verbose
diagnostics included. Alert on the event codes rather than on log
wording.

===== Readiness and the contents of the database

Readiness asserts that the database is *reachable* and that the *schema is
applied*. It deliberately asserts nothing about how much data is in it, and
that distinction is worth stating because it decides what has to be true
before a fleet can be registered with a target group.

The reason it matters is `+SequenceValueItem+`, the entity the readiness
query names. That table is not populated by the schema initialization or by
the data load. The entity engine fills it *on demand*: the first time a
sequenced identifier is asked for under a given sequence name, the engine
logs `+Lock failed; no sequence row was found+` and inserts that one row.
Data files carry their primary keys explicitly, so importing them asks for
no sequenced identifier at all - which means the table is legitimately
*empty* after `+OFBIZ_DATA_LOAD=seed+` or `+none+`, on a schema that is
complete and seed data that is present. A readiness check that required a
non-empty count - the rule the framework's `+ping+` service applies, which
reports `+CommonPingDatasourceInvalidCount+` for a zero count - would
therefore hold a correctly initialized `+seed+` fleet out of its target
group until something happened to perform a sequenced write.

*So it does not require one.* The query is a count under a predicate that
can match no row, and any successful execution is the verdict:

* `+OFBIZ_DATA_LOAD=demo+`, `+seed+` and `+none+` are all `+200+`, as soon
  as the schema is there;
* a database with *no schema applied* is `+503+` under
  `+HEALTH-READINESS-DATASOURCE-UNAVAILABLE+`, because the query fails on a
  relation that does not exist. Run the schema initialization step described
  under _Database_ before starting a serving instance;
* a database that cannot be reached at all is the same `+503+` and the same
  code, which is the honest grouping: both say "fix the database", and the
  log line behind the code carries which of the two it was.

Two further consequences of naming no column in that query are worth
knowing. Renaming or dropping a field of `+SequenceValueItem+` cannot take a
fleet out of its target group, because the probe has no opinion about the
entity's fields; and the query is constant work whatever the table grows
to, so readiness does not become slower as a deployment ages.

Never point a target group at `+/webtools/health/live+` in place of the
readiness path: liveness answers `+200+` while the datasource is
unreachable, which is exactly the situation a target group must not route
into.

===== Running more than one instance

Each instance keeps its own in-memory entity caches. On a single node
that is invisible, but as soon as two instances share one database an
update applied by one of them leaves the other serving the value it
cached earlier, for as long as that entry lives. Set
`+OFBIZ_DISTRIBUTED_CACHE_CLEAR=true+` on every instance of a fleet to
turn that off: the container renders
`+/ofbiz/config/entityengine.xml+` with
`+distributed-cache-clear-enabled="true"+` on the `+default+` and
`+default-no-eca+` delegators, which is what makes the delegator publish
and consume invalidation messages. It works on embedded H2 as well as on a
managed database, so the behaviour can be exercised locally. The flag is
necessary but *not sufficient*: the plumbing it activates needs a message
transport, and no image can ship a broker - so supplying one, with the
`+OFBIZ_JMS_*+` variables below, is part of enabling the flag rather than
an optional extra.

Two things are deliberately left alone. The `+test+` delegator never
receives the flag - it is a single-JVM integration-test delegator, and
the container refuses to start if a configuration enables invalidation
on it. And no new plumbing is introduced: the flag activates the
`+DistributedCacheClear+` implementation OFBiz already ships,
`+org.apache.ofbiz.entityext.cache.EntityCacheServices+`, running as the
`+system+` user, both of which are schema defaults.

Invalidation travels over the `+serviceMessenger+` JMS topic in
`+framework/service/config/serviceengine.xml+`, and that topic is
commented out in the distribution, so a stock image has no transport for
it at all. To run a cache-coherent fleet, supply the transport as well:

. Run a JMS broker that every instance can reach, on TLS and with
authentication - see _Securing the cache transport_ below, which is a
requirement of a deployed fleet rather than a hardening suggestion.
. Add the client library of that broker to `+/ofbiz/lib-extra+`, which
precedes `+/ofbiz/lib+` on the class path. The image ships the JMS 1.1 API
only (`+geronimo-jms_1.1_spec+`, the `+javax.jms+` package) and no
provider implementation, so the client library has to implement
`+javax.jms+`. A client that only provides the newer `+jakarta.jms+`
package will not work here. Add the JMS API jar that client was compiled
against as well, along with the client's own runtime dependencies:
current `+javax.jms+` clients are built against JMS 2.0 and declare
methods returning `+javax.jms.JMSContext+`, a class the shipped 1.1 spec
does not contain, so the connection factory fails to link with
`+NoClassDefFoundError: javax/jms/JMSContext+` on the listener thread -
after the start-up checks described below have already passed,
because a class that resolves by name can still fail to link. Since
`+/ofbiz/lib-extra+` precedes `+/ofbiz/lib+`, a JMS 2.0 `+javax.jms+` API
jar placed there shadows the shipped 1.1 spec, and OFBiz's own JMS 1.1
calls keep working against it unchanged. Apache ActiveMQ Classic 5.19.x,
for example, needs three jars: `+activemq-client+` itself,
`+org.fusesource.hawtbuf:hawtbuf+`, and the JMS 2.0 API jar the client is
built against - which is published as `+jakarta.jms:jakarta.jms-api+` 2.0.3
and, despite those coordinates, still contains the `+javax.jms+` packages
and no `+jakarta.jms+` ones, because Jakarta EE 8 renamed the Maven
coordinates and the package rename did not happen until 3.0. Its own
`+slf4j-api+` dependency is already on the OFBiz class path and does not
need adding. Choose the line and the artifact carefully: 5.19.x is the
maintained Classic line and 5.18.x reached end of life in March 2025, while
the `+activemq-client-jakarta+` artifact of 5.19.x and the whole 6.x line
use the `+jakarta.jms+` packages and are therefore *not* usable here.
Whichever broker you use, confirm its client's own dependency set from its
published POM rather than from a list in any document, this one included -
those sets change between releases.
. Set `+OFBIZ_JMS_INITIAL_CONTEXT_FACTORY+` and
`+OFBIZ_JMS_PROVIDER_URL+` to that client's JNDI factory class and the
broker's URL. That is what asks the container to render the transport,
which it does as three files under `+/ofbiz/config+`, each mode `+0600+`
and each taking class-path precedence over the copy shipped in
`+ofbiz.jar+`:
.. `+serviceengine.xml+` - an active `+jms-service+` named
`+serviceMessenger+` (`+type="topic"+`, `+listen="true"+`,
`+send-mode="all"+`) whose single `+<server>+` element names the JNDI
server below rather than the shipped `+default+` one;
.. `+jndiservers.xml+` - the catalogue the distribution ships with one
entry added, `+<jndi-server name="ofbizCacheTransport"/>+`, carrying the
factory class and the provider URL as its `+initial-context-factory+` and
`+context-provider-url+` attributes. The five entries the distribution
ships, `+default+` included, are copied through untouched;
.. `+jndi.properties+` - the file the distribution ships with the broker's
destination names *appended*: `+topic.<jndi name>+`,
`+connectionFactoryNames+` and `+connectionFactory.<name>+`. The two
properties it already declares, `+java.naming.factory.initial+` and
`+java.naming.provider.url+`, are left exactly as shipped.
. Set `+OFBIZ_DISTRIBUTED_CACHE_CLEAR=true+` on every instance.

That last distinction is not cosmetic. `+jndi.properties+` files are
merged from the class path by the JDK and `+/ofbiz/config+` comes first, so
the two properties that file declares are the JVM-wide default for every
bare `+new InitialContext()+` in the product - including the one
`+CatalinaContainer+` uses to build Tomcat's global naming context while
the instance is still starting, and the two in `+RmiServiceContainer+`.
Repointing them at a broker's factory class replaces the RMI registry
defaults for all of those callers at once, and the instance then fails to
start on a lookup that has nothing to do with caching. Giving the broker
its own named `+jndi-server+` instead confines its settings to the one
lookup that asks for them by name, which is why the shipped `+default+`
server is left parameterless and why the rendered `+serviceMessenger+`
names `+ofbizCacheTransport+`. Each part of that arrangement is verified
after every render: the catalogue must declare exactly one more server
than the distribution ships, `+default+` must still carry no parameters,
and the two standard properties must still match the shipped file byte for
byte - otherwise the render is deleted and the container refuses to start.

marker, and only files carrying it are ever replaced or removed - so
withdrawing the variables removes all three files the container generated,
while a file an operator placed there is left untouched.

Setting the flag without the transport is *not* harmless, so the
container refuses to start - in *every* profile, development included -
when the flag is on and no active `+serviceMessenger+` backs it. It is
refused rather than warned about because continuing would guarantee a
failure that surfaces much later and looks unrelated. The
`+distributedClear*+` services in
`+framework/entityext/servicedef/services.xml+` are declared
`+engine="jms" location="serviceMessenger"+` and are dispatched through
`+ServiceDispatcher.runAsync+`, which - with `+use-transaction+` at its
default of `+true+` - runs inside the caller's transaction: the invalidation is
dispatched to a JMS engine that has no configuration, the resulting
`+NullPointerException+` is caught by the service dispatcher, and the
dispatcher rolls back the transaction of the write that triggered the
invalidation before reporting it. In practice the seed data load aborts
and the container exits, having reported a cache-coherent fleet that never
existed.

Naming a broker is not enough on its own either: if the broker cannot be
reached, the dispatcher rolls the transaction back in exactly the same
way, because that rollback does not depend on why the dispatch failed. So
six things are checked before the instance starts, on every start:

* the rendered or mounted `+serviceMessenger+` declares
  `+listen="true"+`. A send-only instance publishes invalidations and
  ignores everybody else's, which is the failure that looks most like
  success;
* it also declares `+send-mode="all"+`. The attribute has a schema default
  of `+none+`, and `+none+` publishes to an empty server list while any
  other spelling makes the JMS engine throw - so an element that omits it,
  or misspells it, is a fleet that either invalidates nothing or rolls back
  the write that triggered the invalidation. Neither is ever reported ready,
  so it is refused at start up instead;
* the transport satisfies the security policy in _What the broker has to
  be_ below - encryption, hostname verification, a broker principal and the
  topic ACL acknowledgement in the _prod_ profile, and no
  verification-disabling parameter in any profile. This is checked against
  whichever declaration is authoritative, so a mounted `+serviceengine.xml+`
  is held to it exactly as a rendered one is;
* the JNDI factory class it names resolves on the class path, so a missing
  or misnamed `+/ofbiz/lib-extra+` client is reported by name;
* at least one `+host:port+` in the provider URL accepts a TCP connection
  within `+OFBIZ_JMS_CONNECT_TIMEOUT+`. A well-formed URL that names no
  `+host:port+` at all - an in-JVM `+vm://+` broker, or a discovery
  transport that finds its own - cannot be probed; the start proceeds, and
  the acceptance line says that nothing has confirmed a broker answers
  rather than reporting a connection it never made. A URL that no client
  could connect through - `+tcp://+`, `+tcp://:61616+`, an unbracketed IPv6
  literal with a port - is a different finding and *aborts the start up*,
  naming the offending text.

*Once the instance is running, the transport is not checked again, and it is
deliberately not a readiness dimension.* `+/webtools/health/ready+` reports
the datasource and nothing else, so a broker that goes away does not drain
the fleet: `+serviceMessenger+` is one broker shared by every instance, so a
readiness dimension over it would fail on all of them at the same moment and
empty the target group - withdrawing an application that is still serving
every page correctly, and turning stale caches into an outage. The start-up
checks above are where a transport misconfiguration is caught, because that
is the point at which it can still be corrected before traffic arrives.

What that means operationally is that a broker outage shows up as *stale
caches*, not as a `+503+`, and it has to be monitored where it lives. Watch
the broker itself - subscriber count on the topic, connection errors in its
own log - and watch each instance's log for
`+distributedClearCacheLine+` errors, which is what an instance writes when
it cannot publish an invalidation. The listener retries by itself, so an
instance rejoins the topic when the broker returns, with no restart and no
change in what any probe reports.

The invalidation mechanism itself is OFBiz's own and is not modified by this
image: `+DistributedCacheClear+`, its `+EntityCacheServices+` implementation
and the `+serviceMessenger+` topic all ship with the framework and are
covered by the framework's own test tiers. What this image adds is the
ability to turn the per-delegator flag on from the environment - so the
thing to verify in a deployment is the deployment half: a specific
broker, a specific client library, specific credentials and a specific
topic. Run the two-instance check once, before the fleet carries traffic.
Run both instances against the same database with the
flag set and the topic configured, change one cached record through
instance A (Web Tools -> Entity Data Maintenance is enough), then read the
same record through instance B without restarting it and without clearing
its cache. B has to report the new value, and neither log may contain a
`+distributedClearCacheLine+` error. Repeating the check with the flag left
at _false_ shows B still serving the stale value, which is the single-node
behaviour this image ships. A plaintext broker is acceptable for an
isolated local topology, but repeat the check against the deployment's own
TLS and authenticated broker, since a certificate or authorization mistake
shows up as a subscriber that never connects rather than as a start-up
failure. Until a broker is available, run a single instance - or accept
independent caches with sticky sessions at the load balancer and a shorter
cache expiry for the entities that are updated most.

Leaving `+OFBIZ_DISTRIBUTED_CACHE_CLEAR+` at its default of _false_ is
correct for a single instance, and is the behaviour this image has always
had.

====== What the broker has to be

Read this section before enabling the flag in production. The invalidation
topic is not a side channel: what OFBiz publishes on it, and what it does
with what it receives, means that *the broker is the security boundary for
this feature*, and the container enforces what it can from its own side and
tells you plainly what it cannot.

What the container enforces, in the _prod_ profile, on whichever transport
declaration is authoritative - rendered from the variables above or mounted
by you:

* *every endpoint is encrypted.* A TLS scheme - `+ssl+`, `+tls+`,
  `+ssl+nio+`, `+nio+ssl+`, `+amqps+`, `+amqpwss+`, `+mqtts+`, `+wss+`,
  `+https+`, `+stomp+ssl+` or `+stomp+nio+ssl+`, compared without regard to
  letter case - or a parameter that switches TLS on with a true value, is
  required for *each* endpoint of a failover or wrapper URL, not merely for
  the first one: a list whose first member is TLS and whose second is
  plaintext downgrades itself on the first broker restart. A URL that spells
  encryption in a way this check cannot recognise is refused rather than
  assumed, which is the safe direction for this particular question;
* *every endpoint verifies the broker's hostname*, shown either by a
  parameter in the URL or by `+OFBIZ_JMS_TLS_HOSTNAME_VERIFICATION=client-default+`;
* *the connection authenticates*, so `+OFBIZ_JMS_USERNAME+` and
  `+OFBIZ_JMS_PASSWORD+` are required. On a mounted declaration the
  equivalent is the `+<server>+` element's own `+username+` and
  `+password+` attributes, which is the only place the OFBiz JMS stack takes
  a broker principal from;
* *the topic ACL is acknowledged* with
  `+OFBIZ_JMS_TOPIC_ACL_ACKNOWLEDGED=true+`.

And in *every* profile, development included: a provider URL carrying a
parameter that *disables* hostname verification is refused. The refusal
names the parameter key and never its value, and it recognises the shape of
such a parameter rather than a fixed list of spellings, so a client-specific
name it has never seen is still caught.

Beyond that, five limitations are inherent to the plumbing this flag
activates. They live in the Entity and Service engine internals and in the
`+DistributedCacheClear+` implementation OFBiz already ships, all of which
this change set treats as frozen - it activates and parameterizes that
plumbing rather than replacing it (technical specification sections 0.1.2,
0.2.1, 0.3.2 and 0.7.2). They are stated here because each one changes how
a fleet should be operated:

* *Coherence is eventual, not transactional.* The invalidation is published
  *before* the writing transaction commits, over a topic that is not
  enlisted in that transaction. A peer can therefore process the message,
  re-read the row, and cache the *pre-write* value - and keep it until
  something else invalidates that line. The window is the writer's commit
  latency. A deployment that cannot accept it should leave the flag off, or
  shorten the affected caches' expiry in `+cache.properties+` so that a
  missed invalidation self-corrects;
* *A publisher on the topic can invoke exported services.* The listener
  admits any service declared `+export="true"+` - 24 of them in this
  distribution - named in a broker message, and does so with the principal
  the message supplies. The listener itself performs no authorization. This
  is why the ACL matters: it must confine publish *and* subscribe on this
  topic to this fleet's own principal, and it is enforced by the broker, not
  by this container;
* *A message is deserialized before anything authenticates it.* The body
  reaches Java deserialization under an allow-list of `+java..*+` and
  `+org.apache.ofbiz..*+` before the service it names authenticates
  anything. The broker's authentication and ACL are what stand between a
  publisher and object construction inside the JVM;
* *Every invalidation builds its own broker plumbing, unbounded.* A fresh
  JNDI context, connection, session and publisher are created per
  invalidation with no timeout, and a failed publish closes none of them. A
  slow or half-open broker therefore stalls the entity write that triggered
  the invalidation, and a failing one leaks connections. Bound it from
  outside the application: client-side connect and request timeouts in the
  provider URL, a broker-side connection limit for this principal, and
  monitoring of that principal's connection count. The start-up reachability
  check detects a broker that is unreachable *at start*, not one that
  degrades later;
* *Read access to the topic is equivalent to holding the cache-clear
  account's credential.* Each message carries the full written row *and* the
  full `+UserLogin+` row of `+distributed-cache-clear-user-login-id+` - the
  `+system+` account by default - including its stored password hash, which
  is exactly the credential the service dispatcher accepts. Three
  consequences: TLS is mandatory in production and is why it is enforced
  above; the ACL must exclude every other principal; and verbose logging
  must stay off in production, because the listener and `+EntityCacheServices+`
  write the deserialized context and the whole entity value at `+VERBOSE+`.

====== Content that every instance can reach

A fleet also needs somewhere to put content that every instance can
reach. Leave `+OFBIZ_CONTENT_STORE_PROVIDER+` at its default of
`+database+`, or set it to `+s3+` with a bucket every instance shares -
uploads are then written to that bucket by the upload itself, so nothing
has to be copied afterwards. Do *not* select `+filesystem+` for a fleet
unless every instance mounts the same shared volume: that backend reads
and writes the instance's own `+runtime/uploads+` tree, so a file uploaded
through one instance is missing from every other one and is lost when that
instance is replaced. See _Object storage for content_ below.
Content that predates the switch is yours to copy into the bucket once -
see _How content reaches and leaves the object store_ below.

Everything a fleet needs is in the sections above, so here is the whole of
it in one list. An instance is freely replaceable once all seven hold, and
each item is where the state that would otherwise be local goes instead:

* *a database every instance shares.* Set `+OFBIZ_POSTGRES_HOST+` and the
rest of the managed-database settings, pointed at a managed PostgreSQL
service rather than at a container of its own. Embedded H2 is a file on one
instance's volume and cannot be shared - see _Database_ below;
* *the schema applied by the one-shot initialization only.* Run
`+OFBIZ_SCHEMA_INIT=true+` once, let it exit `+0+`, and start the serving
instances with it unset so none of them issues DDL or needs the privilege
to - see _Schema initialization_ below;
* *the same secrets on every instance, from the environment.* Set
`+OFBIZ_PROFILE=prod+` and supply `+OFBIZ_ADMIN_KEY+`,
`+OFBIZ_LOGIN_SECRET_KEY+` and `+OFBIZ_JWT_TOKEN_KEY+` from the platform's
secret store. The `+dev+` profile generates them *per container*, so a
fleet on `+dev+` is a fleet whose tokens and encrypted fields are valid on
one instance only - see _Secrets_ above;
* *content in a store every instance reaches.* Leave
`+OFBIZ_CONTENT_STORE_PROVIDER+` at `+database+`, or set it to `+s3+` with
one shared bucket. `+filesystem+` needs a shared volume to be fleet-safe -
see _Object storage for content_ below;
* *cache invalidation switched on.* `+OFBIZ_DISTRIBUTED_CACHE_CLEAR=true+`
on every instance, with the `+OFBIZ_JMS_*+` transport it requires, per this
section;
* *the readiness endpoint wired to the target group.*
`+/webtools/health/ready+`, so an instance that loses a readiness
dimension is drained rather than served through - and
`+/webtools/health/live+` wherever the platform decides whether to restart
a container. See _Health and readiness endpoints_ above;
* *a route id per instance.* A distinct `+OFBIZ_JVM_ROUTE+` for sticky
sessions, and `+OFBIZ_SSL_ACCELERATOR_PORT+` when the balancer terminates
TLS - see _Load balancers and TLS-terminating proxies_ above, and read the
session limitation below before relying on stickiness.

====== Securing the cache transport

*Treat the invalidation topic as a channel carrying production data, not as
a control channel carrying hints.* `+EntityCacheServices+` publishes the
entity value, the primary key or the `+EntityCondition+` whose cache entry
is being cleared, together with the `+UserLogin+` the invalidation runs as.
Field values therefore travel over the topic. Anyone who can read it reads
those values; anyone who can write to it can invalidate arbitrary cache
entries across the whole fleet - and, because the receiving side acts on
what it is told, can be used to drive the fleet's cache from outside it.

Four requirements follow, all of which belong to the broker and the network
rather than to any `+OFBIZ_*+` variable. None of them is enforced by the
container, which cannot inspect the broker's configuration, so they are
yours to satisfy:

* *Encrypt the transport.* Use the broker's TLS listener -
`+ssl://broker.internal:61617+` for the ActiveMQ Classic client, or the
equivalent scheme or connection option for whichever client you use. Set
`+OFBIZ_JMS_PROVIDER_URL+` to that, never to a plaintext `+tcp://+` URL, in
any deployment where the topic leaves a single host.
* *Verify the broker's certificate.* Encryption without a verified peer
leaves the topic open to anyone who can answer on the broker's address, so
give the client a trust store containing the broker's certification
authority, and keep the client's own host-name verification enabled. Most
clients accept a trust store through `+JAVA_OPTS+`
(`+-Djavax.net.ssl.trustStore=...+`), which the container passes through to
the JVM; a client-specific URL option is the other way. Do not disable
verification to get the connection working - the failure it is reporting is
the one this requirement exists to prevent.
* *Authenticate.* Set `+OFBIZ_JMS_USERNAME+` and `+OFBIZ_JMS_PASSWORD+` and
give the broker an authorization policy that admits only the fleet's
identity to the invalidation topic. An anonymous topic is writable by
anything that can reach the port.
* *Restrict the network.* Put the broker on a private network or subnet that
admits the fleet alone, enforced by a security group or firewall rule, and
do not publish its port. This is the control that still holds when one of
the others is misconfigured.

A plaintext `+tcp://+` URL, and a broker that accepts anonymous
connections, are for an *isolated local development* topology only - a
single host, a private container network, no route in from anywhere else -
where they let the behaviour be exercised without a certificate. The
two-instance propagation check above is written for exactly that case. Do
not carry either of them into a deployment.

The container's start-up checks are about *reachability and wiring*, not
about security: they confirm that the listener is configured to listen,
that the JNDI factory class resolves, and that a `+host:port+` in the
provider URL accepts a TCP connection. A plaintext broker passes all three.
Nothing in the container will tell you the topic is unencrypted or
unauthenticated, which is why the four requirements above have to be
checked at the broker.

====== Sessions do not survive the instance that created them

This is a limitation to plan around, not a setting to change, and it is
stated plainly here because the alternative is discovering it during a
deployment.

HTTP sessions are *instance-local*. Each session lives in the memory of the
one instance that created it, and this image configures no replication and
no external session store: `+apps-distributable+` is _false_, the Tomcat
cluster/session-replication block in
`+framework/catalina/ofbiz-component.xml+` ships commented out, and nothing
persists a session outside its JVM. So when an instance is replaced, scaled
in, restarted or lost, *every session it held is lost with it*, and the
users holding those sessions are signed out and have to sign in again on
whichever instance they reach next.

`+OFBIZ_JVM_ROUTE+` does not change this. It is *sticky-routing metadata
only*: it appends the instance's id to the session cookie so a load
balancer configured for sticky sessions can send a returning request back
to the instance that owns the session. It carries no session data and
enables no failover - there is nothing to fail over to. Sticky routing
keeps a session usable while its instance is alive; it cannot restore one
afterwards. Set it, per _Load balancers and TLS-terminating proxies_ above,
because without it a balancer cannot even find the owning instance; just do
not read it as high availability for sessions.

`+OFBIZ_ENABLE_CROSS_SUBDOMAIN_SESSIONS+` does not change it either, and on
this release it does not do what its name promises.
`+CrossSubdomainSessionValve+` widens the session cookie's `+Domain+`
attribute by searching the *request* header set for the `+Set-Cookie+` header
it means to rewrite - but a request never carries that header, so the widened
`+Domain+` is never emitted and a session cookie stays scoped to the host that
issued it. What the valve does do on every request is call
`+request.getSession(true)+`, forcing a session to exist, on every path
without exception - a health probe included, though the probe endpoint then
discards the session made for it, so the valve costs a probed instance nothing
that outlives the probe (see _Health and readiness endpoints_ above). The cost
is therefore paid whether or not the sharing it exists to provide takes
effect. This is long-standing upstream
behaviour that this change set deliberately leaves alone, and it is recorded
here so the knob is not switched on in the expectation of cross-sub-domain
sharing. A multi-instance deployment does not need it; sticky routing plus the
draining discipline below is what it needs.

What this does *not* compromise is the statelessness the rest of this
document describes. An instance holds no *durable* state: the database
holds the data, the object store holds the file-backed content when
`+OFBIZ_CONTENT_STORE_PROVIDER=s3+` - written there by the upload itself,
rather than copied there afterwards - the schema is applied by the separate
initialization run, and the entity caches are kept coherent by distributed
cache clear. That is what makes an instance freely replaceable, and neither
a read nor a write through the store leaves anything on local disk to
account for. Content that predates the switch is the one exception, and it
is bounded: it is yours to copy into the bucket once, and it keeps serving
from the local copy until you do - see _How content reaches and leaves the
object store_ below. A session is the one piece of state that is not
durable, and it is recoverable by signing in again - which durable state is
not.

*So state the fleet's shape without overclaiming.* This is a *sticky*
fleet whose instances are replaceable *at the cost of signing out the users
whose sessions they held*. It is not a fleet whose instances are
interchangeable mid-session, and no statelessness claim anywhere in this
document should be read as saying so.

Every such claim here is about *durable* state, and about that it holds: the
database holds the data; the object store holds the file-backed content and
the uploads when `+OFBIZ_CONTENT_STORE_PROVIDER=s3+`, published as the
recording transaction commits rather than copied in afterwards; a file on an
instance's own disk is a read-through cache of the store, rebuildable from it
by any instance and never the only copy of anything; the schema is applied by
the separate initialization run; the entity caches are kept coherent by distributed cache clear; and a
health probe leaves nothing behind, the session the filter chain creates for it
included. Session state is
the one category that is neither durable nor externalised, and it is
*recoverable by signing in again* - which durable state is not. That is why
it is accepted here rather than solved.

Three practical consequences:

* *Configure sticky routing, or the cost arrives earlier than replacement.*
Without it a returning request can land on an instance that never held the
session, so users are signed out on the *next request* rather than when an
instance is replaced. `+OFBIZ_JVM_ROUTE+` is what lets a balancer do it.
* *Drain before terminating.* Deregister an instance from the load
balancer and let its in-flight requests finish before stopping it, so
sessions end at a moment you chose. Readiness answering 503 is the signal a
target group acts on, so an instance that is being drained should be taken
out of the target group rather than merely stopped.
* *A rolling deployment signs everyone out.* Rolling every instance
replaces every session. Schedule accordingly, or expect the sign-in
prompt.

If a deployment genuinely requires sessions to outlive an instance, that is
a separate change with its own transport, serialization and operational
cost - Tomcat session replication over the commented-out cluster block, or
an external session store - and it is deliberately not part of this image.

===== Content and upload storage

An instance that keeps content on its own disk is not replaceable: a
document uploaded through one instance is invisible to every other one
and is lost when that container is replaced. Selecting an S3-compatible
object store instead makes every instance read *and write* file-backed
content through one bucket, so an upload is readable by every instance the
moment it completes, no instance depends on a file only it holds, and no
upload is lost with the instance that received it. _How content reaches and
leaves the object store_ below states exactly which operations reach the
store, what a rollback does, and what stays local. Content written before
the switch is the one thing an upload cannot place there for you, and is
yours to copy in once.

`+DataResource+` content and uploaded files: `+database+` (the
`+DataResource+` columns, the behaviour of an unconfigured checkout),
`+filesystem+` (the instance's own `+runtime/uploads+` tree) or `+s3+`
(an S3-compatible object store). Compared after trimming and folding

The values are written into `+/ofbiz/config/content.properties+`, which
precedes `+ofbiz.jar+` on the class path, and are read by
`+ContentStoreFactory+`. Each variable sets the property of the same name:
`+OFBIZ_CONTENT_STORE_PROVIDER+` sets `+content.store.provider+`, and the
six `+OFBIZ_S3_*+` variables set `+content.store.s3.bucket+`,
`+content.store.s3.region+`, `+content.store.s3.endpoint+`,
`+content.store.s3.access.key.id+`,
`+content.store.s3.secret.access.key+` and
`+content.store.s3.path.style+`. With nothing configured the rendered file
reproduces the committed one exactly, so an unconfigured container - the
embedded H2 run - keeps storing content in the database and the object
store code is never reached.

Selecting _s3_ without a bucket or a region aborts the start up. That
check earns its keep because the client resolves its configuration
without contacting the network, so an incomplete configuration is
otherwise not reported until the first content operation fails, long
after the instance has been declared healthy. Missing or wrong
credentials cannot be detected this way and will surface at that first
content operation, so exercise one before putting an instance into a target
group. Uploading a document through the content manager does exercise it:
the upload lands on the instance's own disk, and the transaction that
recorded it publishes that file to the store as it commits, so the endpoint,
the credential and the bucket are all exercised by a single upload - and the
instance's log names the key it published under. Reading the same document
back afterwards, on an instance that has no local copy of it, exercises the
read direction as well. If it is easier to test without an upload, put one
object into the bucket yourself under the exact key the provider will ask
for - the configured `+content.store.s3.key.prefix+` followed by the
content's `+/ofbiz+`-relative path, derived in _How content reaches and
leaves the object store_ below - point a `+DataResource+` row of a
file-backed type at that same path, and read it through OFBiz. Either way a
read that succeeds has exercised the endpoint, the credential, the bucket
and the key derivation together, and a read that fails names which of them
refused.

One caveat applies to reading an upload back, and it is not this image's
doing: OFBiz ships `+content.data.local.file.allowed.paths+` set to
`+${ofbiz.home}/runtime/tmp/+`, while its own upload flow writes under
`+runtime/uploads+`, so a `+LOCAL_FILE+` resource written by an upload is
refused by the file allow list before any storage provider is consulted.
That refusal is upstream behaviour and is unchanged here. A deployment
routing uploads through an object store should point its rows at the
`+OFBIZ_FILE+` types, which the shipped
`+content.data.ofbiz.file.allowed.paths+` already admits for
`+runtime/+`, or widen the local-file allow list to include its upload
directory. The allow list is checked *before* the store is asked, so a
refused read costs no request and leaks nothing about the bucket.

A bucket that is not there is reported as a failure, not as missing
content. Every operation - reading, streaming, testing for existence and
deleting - treats "the bucket does not answer for this deployment" as a
configuration failure rather than as "the bucket holds no such object",
because only the store's own `+NoSuchKey+` means the second. A `+404+`
that carries no error code at all, which is what an endpoint that is not
an object store answers with, is a failure for the same reason. Testing for
existence deserves the specific note, because it is the operation where a
mis-typed bucket most easily looks like an empty one. A `+HEAD+` could not
tell the two apart - it carries no response body, so the SDK has no error
code to model and reports an absent bucket exactly as it reports an absent
key - so existence is asked with a one-byte ranged `+GET+` instead, whose
error document names the missing thing: `+NoSuchKey+` is reported as
absence, `+NoSuchBucket+` and `+AccessDenied+` as the failures they are. A
range that lies past the end of the object is the one error that means the
object *exists* - it is what a zero-length object answers - and is reported
as present. The response is aborted rather than read, so the test costs what
the `+HEAD+` would have cost plus one byte, and it needs no permission
beyond the `+s3:GetObject+` a read already requires. A delete likewise fails
rather than reporting success, so a mis-typed
`+OFBIZ_S3_BUCKET+` cannot look like a fleet that is quietly working.
None of those failures reproduces the bucket, the key or the store's own
words in what the caller sees - each carries an opaque reference instead -
and the log line behind that reference is where to look. That line is
itself redacted by default: it names the reference, the operation, the key
and the bucket, and of the store's answer only the HTTP status, the error
code and the request id, so a failure can be correlated with the store's
own logs without the OFBiz log becoming a transcript of what the store
said. A client-side failure that never reached the store is named by
exception type alone, for the same reason.

*There is deliberately no verbose switch that widens this*, and that is worth
knowing before looking for one. The SDK failure is handed to the logging
framework in no form at all: an SDK message can quote the request it was
building, endpoint and signed headers included, and logging the exception
object writes its message together with its whole stack trace - the one route
that bypasses the redaction above, and one that a `+verbose+` category could
be switched on for reasons having nothing to do with content storage. What
the redacted line already carries - the failure type, and for a failure the
store answered the HTTP status, the error code and the request id - is what
identifies a failure; the store's own logs, joined by that request id, are
where its own words are. So when the redacted line is not enough, take the
request id to the object store rather than raising the OFBiz log level.

*The same redacted facts are also available programmatically*, which matters
for code that has to act on a failure rather than read about one. The
exception a caller receives carries a cause holding exactly what the log line
holds - the failure type, the HTTP status, the store's error code and the
request id - and nothing else: it is a purpose-built value with no cause of
its own, no suppressed exceptions and no stack trace, and it is not an SDK
type, so no SDK class or message escapes the storage contract through it.
Client-side failures report a status of `+-1+`, which is how "this never
reached the store" is told apart from a status the store returned. The outward
message is unchanged and still discloses neither bucket nor key.

Switching provider does not move anything, and this is the one respect in
which the two providers are *not* interchangeable. They derive the same key
for the same content - the content's own `+/ofbiz+`-relative path - so
neither has to be re-keyed and nothing has to be looked up to translate
between them; what a switch does not do is copy the bytes. Content the
previous provider holds stays where it is, so plan a switch as a migration:
copy the existing content across first - path for path, with the script in
_How content reaches and leaves the object store_ below - or accept that
older documents resolve only through the provider that stored them, which
`+content.store.local.fallback+` makes survivable in one direction only,
from `+filesystem+` to `+s3+`.

==== Secrets

OFBiz needs three secret values at run time. None of them is stored in
the source tree, in the distribution tarball or in any container image
layer, so each one has to be supplied to the container through an
environment variable.

[width="100%",cols="34%,33%,33%",options="header",]
|===
|Environment variable |Default |Description
|OFBIZ_ADMIN_KEY |_unset_ |Shared secret that authenticates a request on
the OFBiz admin port - the port that can shut the JVM down, so treat it as a
credential of the same weight as the two below. Rendered into
`+/ofbiz/config/org/apache/ofbiz/base/start/start.properties+` and nowhere
else: that mode `+0600+` file on the configuration volume precedes
`+ofbiz.jar+` on the class path, so it is what the JVM reads, and no second
copy is written into the image's writable layer where an export or a commit
could capture it. Must be at least 16 characters and must not contain a
colon, because the admin port protocol splits an incoming request on the
first colon. *It is not how you stop a container* - see _Stopping a
container_ below.

|OFBIZ_LOGIN_SECRET_KEY |_unset_ |Value of
`+login.secret_key_string+`, which names the `+EntityKeyStore+` entry
protecting the forgot-password token. Rendered into
`+/ofbiz/config/security.properties+`. Must be at least 64 characters -
the same 512 bit floor as the JWT key below, applied to both signing keys
by one rule.

|OFBIZ_JWT_TOKEN_KEY |_unset_ |Value of `+security.token.key+`, the key
that signs and verifies OFBiz JSON Web Tokens. Rendered into
`+/ofbiz/config/security.properties+`. Must be at least 64 characters:
OFBiz signs with HMAC512, so the key has to carry 512 bits - which is 64
characters - and `+JWTManager+` rejects a shorter one outright.
|===

A fourth secret applies only to a multi-instance deployment that enables
cross-instance cache invalidation against an authenticating broker:
`+OFBIZ_JMS_PASSWORD+`, rendered into the transport declaration in
`+/ofbiz/config/serviceengine.xml+`. It is handled exactly like the three
above - never written to a command line, never logged, removed from the
environment before any child process runs - but it has no minimum length
or entropy floor, because a broker password is chosen by the broker's
administrator. It may be absent for a broker that does not authenticate,
which is accepted in _dev_ and *refused in _prod_*: read _What the broker
has to be_ under _Running more than one instance_ before deciding that an
anonymous broker is acceptable, because subscribe access to that topic is
equivalent to holding a credential. See _Running more than one instance_ for
the rest of the transport configuration.

A supplied value is rejected, and the container refuses to start, when
it is blank, is the literal `+NA+`, is shorter than the minimum length
above, uses fewer than eight distinct characters, or contains a control
character such as a newline or a NUL. A value drawn at random from any
alphabet of sixteen or more symbols passes the distinct character floor
with overwhelming probability, so only hand typed placeholders such as
`+abababababababab+` are turned away. Rejection messages name the
environment variable and the reason but never echo the value.

Absence is checked for the whole set at once, before the first value is
used, so a container that is missing several required secrets names all of
them in one message instead of reporting the first, being restarted, and
reporting the next. That set is the three secrets above whenever
`+OFBIZ_PROFILE+` is `+prod+`, plus the three managed database passwords
whenever `+OFBIZ_POSTGRES_HOST+` is set. A value that is present but
unusable is still reported on its own, by the check that reads it.

`+OFBIZ_PROFILE+` decides what happens when a secret is absent or
rejected:

* `+prod+` - the container refuses to start. This is the intended
setting for any deployment that serves real traffic, and for every
multi-instance deployment, because the same three values have to be given
to every instance. Each has a different reason, and it is worth being
precise about them:
+
--
** `+OFBIZ_JWT_TOKEN_KEY+` signs and verifies OFBiz JSON Web Tokens, so a
token one instance issued is only accepted by another instance holding the
same key.
** `+OFBIZ_LOGIN_SECRET_KEY+` names the `+EntityKeyStore+` entry that
protects stored forgot-password material, so a reset started on one
instance is only completable on another holding the same key.
** `+OFBIZ_ADMIN_KEY+` authenticates a request on the admin port, so an
orchestrator's shutdown signal has to carry the value the instance it is
addressing was given.

*None of the three transports or preserves an HTTP session.* Sessions are
instance-local and are not replicated by this image, so giving every
instance identical secrets does not make a session survive the instance
that created it - see _Sessions do not survive the instance that created
them_ above. Sticky routing keeps a session usable while its instance is
alive and cannot restore one afterwards; durable sessions would need
Tomcat session replication or an external session store, neither of which
this image configures.
--

* `+dev+` - a random value is generated so that an unconfigured container
still boots, which keeps the demo image usable. The generated values are
kept under `+/ofbiz/runtime/container_state/generated_secrets+`, in files
only the `+ofbiz+` user can read, and are reused on every restart of that
container. They are per container, so they are unsuitable for a
multi-instance deployment.

An unset `+OFBIZ_PROFILE+` selects `+dev+`, and the container writes a
`+NOTICE+` naming the assumed profile so that the choice appears in the
log rather than being made silently. A value that is neither `+dev+` nor
`+prod+` - including one that is only whitespace - aborts the start up,
and `+prod+` is never assumed: a deployment that serves real traffic has
to name it.

Generated key material never outlives its usefulness:

* Supplying a variable that was previously generated *destroys* the
stored generated value, so a later start that omits the variable draws
fresh material instead of reviving the retired key.
* A `+prod+` start deletes every stored generated value before it
resolves a single secret, so a volume that was last used by a `+dev+`
container cannot supply key material to a deployed one.

`+OFBIZ_LOGIN_SECRET_KEY+` and `+OFBIZ_JWT_TOKEN_KEY+` must be
*different* values, in both profiles. They protect different things -
stored forgot-password material and JWT signatures - and the token key is
handled by far more code and travels with every issued token, so sharing
one value would make a compromise of the token key a compromise of the
stored material as well.

*No secret may begin or end with a space, a tab or a form feed.* Such a
value is refused, naming the variable, because the application would not
run on the value that was validated: `+java.util.Properties+` discards the
blanks before a value, and `+UtilProperties.getPropertyValue+` - which every
consumer of these properties calls - trims both ends. A 64 character signing
key with one trailing space is therefore checked at 64 characters and used
at 63, below the floor the check just enforced, and it is a value nobody can
type back or rotate to. Whitespace *inside* a value is fine and round trips
untouched. The same refusal applies to `+OFBIZ_HOST+`, whose consumer splits
it on commas without trimming the parts, and to the object-store bucket,
region, endpoint and credentials. `+OFBIZ_CONTENT_URL_PREFIX+` is the one
value where only a *leading* blank is refused: a trailing one names the same
origin once trimmed, so refusing it would be an arbitrary restriction, and
the rendered file is instead read back and compared as
`+UtilProperties+` will normalise it.

The same rules apply to a value that is *pre-provisioned* rather than
supplied to this start. With `+OFBIZ_SKIP_INIT+` set and no secret in the
environment the rendering *keeps* what `+/ofbiz/config+` already declares
instead of substituting a new value, and a kept value never passes through
the strength tests a supplied one does, so in the `+prod+` profile the
container reads what `+/ofbiz/config+` declares for each of the three
properties and applies exactly the tests above to it. A file that merely
declares the property is not enough: `+ofbiz.admin.key=NA+`, a one
character login key or a JWT key shorter than 64 characters is refused
just as the equivalent environment value would be. The report names the property, the file and
the environment variable that would normally have supplied it, together
with the reason, and never the value. Where a property is declared more
than once the *last* declaration is the one judged, because that is the
one `+java.util.Properties+` resolves to and therefore the one OFBiz
uses.

The three properties are read from where an externally provisioned
configuration is mounted: `+ofbiz.admin.key+` from
`+/ofbiz/config/org/apache/ofbiz/base/start/start.properties+`, and
`+login.secret_key_string+` and `+security.token.key+` from
`+/ofbiz/config/security.properties+`. `+config/+` is the directory that
takes class path precedence over the copies inside `+ofbiz.jar+`, so it is
also where a value supplied through the *environment* is rendered - which
is why supplying the environment variable satisfies the check exactly as a
mounted file does, and why the check is made after the rendering rather
than instead of it. Without this backstop a `+prod+` container started
with `+OFBIZ_SKIP_INIT+` and no secrets anywhere would come up serving
traffic with the image's blank signing keys and an admin key of `+NA+`. A
`+dev+` container with `+OFBIZ_SKIP_INIT+` set behaves exactly as it did
before.

The three variables are handled so that they are not observable from
outside the container:

* Each rendered file is written atomically, is owned by the `+ofbiz+`
user and has mode `+0600+`.
* The values are substituted from a temporary file, never from a command
line argument, so they never appear in the process table.
* The variables are removed from the environment before the entry point
starts any child process at all - not merely before OFBiz is started.
The entry point's first action is to move every secret it was given into
shell state that is not exported, so no initialisation JVM, no hook
script and no OFBiz process is ever handed the value, and none of them
can republish it through `+/proc/<pid>/environ+`, a heap dump or an
`+hs_err+` crash file. Only the export attribute is removed, so the entry
point itself still reads the value and renders it; nothing has to be
supplied twice. The same treatment is applied to every other name on the
script's `+SECRET_ENVIRONMENT_VARIABLES+` list - thirteen in all, these
three and `+OFBIZ_ADMIN_PASSWORD+`, the three
`+OFBIZ_POSTGRES_*_PASSWORD+` and three
`+OFBIZ_POSTGRES_*_INIT_PASSWORD+` variables, `+OFBIZ_S3_ACCESS_KEY_ID+`,
`+OFBIZ_S3_SECRET_ACCESS_KEY+` and `+OFBIZ_JMS_PASSWORD+`.
`+OFBIZ_ADMIN_USER+` is a user name rather than a credential, so it stays
exported and is removed with the rest of the settings just before OFBiz
is executed.
* One residual cannot be closed from inside the container: the entry
point's own `+/proc/<pid>/environ+` is a snapshot the kernel took when
the container started, and a process cannot rewrite it. Anything able to
read that one process's environment still sees what the container was
started with. Deliver secrets as mounted files rather than as
environment variables if that matters in your threat model.
* Rendering starts from the pristine copy shipped in the distribution
and runs on every start, so rotating a secret only takes a restart with
the new value.

Supply the values from the platform's secret store rather than from a
shell, and prefer a file based mechanism such as `+docker run --env-file+`
or a mounted secret over `+--env+` on the command line.

Such a file is plain `+KEY=value+` lines - the same shape as the tracked
`+docker/examples/postgres-demo/ofbiz-postgres.env+`, which carries the
non-secret settings of that example. The `+ofbiz-secrets.env+` named in the
examples throughout this document is a file of your own, holding the three
values and nothing else, and it belongs wherever the deployment keeps its
secrets rather than in this repository:

----
OFBIZ_ADMIN_KEY=<16-or-more-character-secret-with-no-colon>
OFBIZ_LOGIN_SECRET_KEY=<64-character-base64-key>
OFBIZ_JWT_TOKEN_KEY=<a-different-64-character-base64-key>
----

The three angle-bracketed values are placeholders rather than values to
copy - a key that has appeared in a document is a key to rotate. Generate
the two signing keys instead of composing them: 48 random bytes encode to
exactly the 64 base64 characters the 512 bit floor asks for, which is what
the `+dev+` profile generates for itself. A `+prod+` start also requires
`+OFBIZ_ADMIN_PASSWORD+`, described in the _Environment variables_ table
above, and the same file is its natural home.

[source,shell script]
----
umask 077
{
    printf 'OFBIZ_ADMIN_KEY=%s\n'        "$(openssl rand -base64 24)"
    printf 'OFBIZ_LOGIN_SECRET_KEY=%s\n' "$(openssl rand -base64 48)"
    printf 'OFBIZ_JWT_TOKEN_KEY=%s\n'    "$(openssl rand -base64 48)"
} > ofbiz-secrets.env
----

Write the values in such a file *unquoted*. `+docker run --env-file+`
gives no special meaning to quotation marks, so
`+OFBIZ_ADMIN_KEY="s3cret"+` sets a key whose first and last characters
are `+"+`. Compose's `+env_file:+` does strip a matching surrounding pair,
so the same file can behave differently under `+docker run+` and under
`+docker compose+`; the example file in
`+docker/examples/postgres-demo+` is written for Compose. A quoted
password reaches the database as-is and fails authentication, which in a
schema initialization run is reported as a failed initialization rather
than being applied silently.

Do not pass the admin key as a JVM system property, for example with
`+-Dofbiz.admin.key+` or through `+JAVA_OPTS+`. A system property is
visible in `+/proc/<pid>/cmdline+`, is reported by `+ps+` and by
container inspection, and can be captured in a crash dump, so it cannot
be withdrawn once it has been observed.

===== Keeping the signing keys out of the image

`+login.secret_key_string+` and `+security.token.key+` are declared but
left *blank* in `+framework/security/config/security.properties+`. That
file is a main resource - the `+config+` directory of every component is
on the resource source path - so it is copied into
`+build/resources/main+`, sealed into `+ofbiz.jar+`, and copied again
into `+ofbiz.tar+`, which is the archive the image is built from. A value
written into it therefore ends up in an image layer, where overwriting
the file at run time cannot remove it: anybody who can read a layer or
the jar can extract the JWT key and forge tokens.

Two things keep that from happening, and the second one is a rule rather
than a check:

* `+gradlew loadAll+` no longer runs `+generateSecretKeys+`. Loading data
needs no signing key, so the required data-load workflow no longer
touches the tracked file - which is what makes "the tracked file is blank"
the normal state of a checkout rather than something to remember to restore.
* *Never run `+gradlew generateSecretKeys+` in a tree an image will be built
from.* It exists for a developer who wants persistent keys in a local
checkout, and it writes into the tracked file. After running it the tree can
still be run (`+gradlew ofbiz+` needs only `+classes+`) but it must not be
packaged. Restore it with
`+git checkout -- framework/security/config/security.properties+` before
building an image, and confirm with
`+grep -n 'secret_key_string\|security.token.key' framework/security/config/security.properties+`
that both values are blank.

Treat any image built from a populated tree as compromised: delete it,
and rotate `+login.secret_key_string+` and `+security.token.key+` in
every environment that was served from it, because the keys in its
layers can no longer be withdrawn.

==== Stopping a container

Stop it the ordinary way: `+docker stop <container>+`, or whatever the
orchestrator's equivalent is. Nothing inside the image has to be invoked.

The entry point's last statement is `+exec "$@"+`, so the OFBiz JVM
*replaces* the entry-point shell and becomes PID 1 of the container. A
`+docker stop+` therefore delivers `+SIGTERM+` straight to the JVM, which
runs OFBiz's own shutdown - containers stopped, connections closed, caches
released - and exits. The default ten-second grace period is usually enough;
raise it with `+--time+` on a busy instance so that a long request finishes
rather than being killed.

`+/ofbiz/send_ofbiz_stop_signal.sh+` ships in the image and *is not the way
to stop a serving instance.* It reads the admin port and key from
`+/ofbiz/framework/start/src/main/resources/org/apache/ofbiz/base/start/start.properties+`,
which is the source anchor - and this image deliberately leaves
`+ofbiz.admin.key+` commented out there so that no shared secret lives in a
tree that gets packaged into a layer. The value the JVM actually uses is
rendered into `+/ofbiz/config/org/apache/ofbiz/base/start/start.properties+`,
which that helper does not read, so in a container it resolves no key and its
request is refused. The entry point invokes it in exactly one place - a
`+SIGTERM+` that arrives while initialisation is still running and no
initialisation child is in flight - and tolerates its failure, because at
that point no admin port is listening either. Removing the helper is
upstream's call, so it is left where upstream puts it.

If a deployment genuinely needs the admin port to stop an instance, drive it
directly with the key that deployment supplied:

[source,shell script]
----
printf '%s:SHUTDOWN\n' "$OFBIZ_ADMIN_KEY" | curl telnet://localhost:10523
----

but prefer `+docker stop+`: it needs no secret in the caller's hands and it
is what an orchestrator does anyway.

==== Hooks

At various steps of initialisation, the `+docker-entrypoint.sh+` script
will check for '`hook`' scripts in various directories.

Users of the container can mount files into these directories and
influence the OFBiz startup process.

Only script files with filename extension `+.sh+` will be processed. If
the file is executable, it will be executed, otherwise it will be
sourced.

[width="100%",cols="50%,50%",options="header",]
|===
|Directory |Step
|`+/docker-entrypoint-hooks/before-config-applied.d+` |Scripts processed
before configuration, such as modifications to property files, are
applied.

|`+/docker-entrypoint-hooks/after-config-applied.d+` |Scripts processed
after configuration modifications have been applied.

|`+/docker-entrypoint-hooks/before-data-load.d+` |Scripts processed
before data loading is executed. Could be used to apply modifications to
data files.

|`+/docker-entrypoint-hooks/after-data-load.d+` |Scripts processed after
data loading is executed.
|===

A hook runs with *no secret in its environment* and with shell tracing
suspended. Both are necessary: a hook is arbitrary mounted code, and a
sourced hook runs inside `+docker-entrypoint.sh+` itself, so it inherits
whatever the script is holding. A hook that turns tracing on - the
`+docker/examples/postgres-demo+` example hook does exactly that - would
otherwise write every expanded command, secrets included, to the
container log, and any hook that merely fails could echo a value in its
own diagnostics. Tracing is therefore switched off around each hook and
restored afterwards to whatever the *operator* asked for - through
`+OFBIZ_TRACE+`, or through the shell's own `+-x+` flag - no matter what
the hook left it set to, and each of the thirteen secret variables is
removed before the hook runs and restored - with its original export
attribute - afterwards.

The thirteen variables withheld are the admin password
`+OFBIZ_ADMIN_PASSWORD+`; the admin key `+OFBIZ_ADMIN_KEY+`; the two
signing keys `+OFBIZ_LOGIN_SECRET_KEY+` and `+OFBIZ_JWT_TOKEN_KEY+`; the
three serving database passwords `+OFBIZ_POSTGRES_OFBIZ_PASSWORD+`,
`+OFBIZ_POSTGRES_OLAP_PASSWORD+` and
`+OFBIZ_POSTGRES_TENANT_PASSWORD+`; the three initialization database
passwords `+OFBIZ_POSTGRES_OFBIZ_INIT_PASSWORD+`,
`+OFBIZ_POSTGRES_OLAP_INIT_PASSWORD+` and
`+OFBIZ_POSTGRES_TENANT_INIT_PASSWORD+`; the two object-store credentials
`+OFBIZ_S3_ACCESS_KEY_ID+` and `+OFBIZ_S3_SECRET_ACCESS_KEY+`; and the
message broker password `+OFBIZ_JMS_PASSWORD+`. They are the script's own
`+SECRET_ENVIRONMENT_VARIABLES+` list, which is where the policy is
written down once: the same list is what is removed around a hook and
what an allowlist entry is checked against.

*The AWS SDK's own credential inputs are withheld from a hook as well*, and
from every initialization child the container starts. That is the nine
names `+AWS_ACCESS_KEY_ID+`, `+AWS_SECRET_ACCESS_KEY+`,
`+AWS_SESSION_TOKEN+`, `+AWS_SECURITY_TOKEN+`,
`+AWS_WEB_IDENTITY_TOKEN_FILE+`, `+AWS_CONTAINER_AUTHORIZATION_TOKEN+`,
`+AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE+`,
`+AWS_CONTAINER_CREDENTIALS_FULL_URI+` and
`+AWS_CONTAINER_CREDENTIALS_RELATIVE_URI+`. They cannot be withdrawn
permanently the way the `+OFBIZ_*+` secrets are - the SDK resolves them
inside the serving JVM, from the environment, which is how an instance
profile or a task role supplies short-lived credentials - so they are
removed for the duration of a hook and of each initialization child, and
restored, exported, for the process the container finally runs. A data
loader authenticates to no object store, so nothing it does needs them.
`+AWS_REGION+`, `+AWS_MAX_ATTEMPTS+` and `+AWS_RETRY_MODE+` carry no
credential and are left alone throughout. An `+AWS_*+` credential name may
be re-admitted to a hook by naming it in `+OFBIZ_HOOK_SECRET_ALLOWLIST+`,
exactly as an `+OFBIZ_*+` secret can.

Every other `+OFBIZ_*+` variable is readable by a hook, including
`+OFBIZ_ADMIN_USER+`, which is a user name rather than a credential.

A hook that genuinely needs one of the thirteen - for example to configure
a component that authenticates against the same database - must be granted
it explicitly by naming the variable in
`+OFBIZ_HOOK_SECRET_ALLOWLIST+`, which takes a comma or space separated
list:

[source,shell script]
docker run -e OFBIZ_HOOK_SECRET_ALLOWLIST=OFBIZ_POSTGRES_OFBIZ_PASSWORD ...

Only the thirteen names above and the nine `+AWS_*+` credential names are
accepted; anything else, including a misspelling, aborts the start up.
Grant the narrowest set that works, and remember that an allowlisted value
is visible to *every* hook in every stage, and to a trace the hook itself
enables.

There are exactly two supported ways to get a withheld value to a hook,
and *naming it something else is not one of them*:

* name it in `+OFBIZ_HOOK_SECRET_ALLOWLIST+`, exactly as above; or
* mount it as a file the hook reads, scoped as narrowly as the platform's
secret mechanism allows - which is also how a hook can read a value the
way OFBiz itself does, from the rendered file under `+/ofbiz/config+`.

Do *not* copy a secret into a differently-named variable to get round the
allowlist. The withdrawal is by name: the entry point unsets the names it
knows, so a name it does not know is never unset, and a copy under one
stays exported for the whole life of the container. It is therefore
readable by every hook in every stage whether or not that hook was meant to
see it, is inherited by every child process including the OFBiz JVM, and
appears in that process's `+/proc/<pid>/environ+`, in container
inspection and in any heap or crash dump taken from it. An alias is
strictly worse than an allowlist entry: an allowlisted value is exported
only for the duration of each hook that runs and is demoted again the
moment that hook returns, so it never reaches the OFBiz process at all.

==== Data files

During the data loading step - but after either seed or demo data has
been loaded - directory `+/docker-entrypoint-hooks/additional-data.d+`
will be checked to see if any files are present.

If files are present then the load-data functionality in OFBiz will be
executed, specifying the `+/docker-entrypoint-hooks/additional-data.d+`
directory as a data source. Any `+.xml+` files in this directory will be
treated as a data source and will be imported by the entity engine.

This functionality can be used to pre-load OFBiz with user-specific
data, such as a chart of accounts.

==== Database

By default the OFBiz container will use an internal H2 database,
storing database related files in the /ofbiz/runtime volume.

Use of an external database can be configured through environment
variables.

===== What selecting PostgreSQL does and does not change

Two files are involved, and keeping them apart explains everything else in
this section:

* `+framework/entity/config/entityengine.xml+` is the *committed source*.
It is unchanged in its choice of database: the `+default+`,
`+default-no-eca+` and `+test+` delegators all still map
`+org.apache.ofbiz+`, `+org.apache.ofbiz.olap+` and
`+org.apache.ofbiz.tenant+` to the `+localh2+`, `+localh2olap+` and
`+localh2tenant+` datasources. That is why a bare checkout, and a container
started with no database variables, boots on embedded H2 with nothing
configured.
* `+docker/templates/postgres-entityengine.xml+` is the *render template*.
When `+OFBIZ_POSTGRES_HOST+` is set, the entry point substitutes the
database variables into it and writes the result to
`+/ofbiz/config/entityengine.xml+`, which takes class-path precedence over
the copy inside `+ofbiz.jar+`. In that rendered file - and only there - the
`+default+` and `+default-no-eca+` delegators map those same three groups
to `+localpostgres+`, `+localpostgresolap+` and `+localpostgrestenant+`.

Withdrawing the variables removes the rendered override, so the committed
H2 mapping applies again on the next start. PostgreSQL is the default of the
*deployed* profile, not a change to what the repository declares.

Three guarantees follow, and they are worth stating because a deployment
decision rests on each:

* *The `+test+` delegator always stays on H2.* Its three group-maps name
`+localh2+`, `+localh2olap+` and `+localh2tenant+` in the committed source
*and* in the render template, where that mapping is deliberately left
unsubstituted. So `+gradlew testIntegration+` keeps running against
embedded H2 whatever the deployment's own database is, needs no managed
database, credential or network of its own, and cannot write into the
deployment's data. The container also refuses to start if a configuration
enables distributed cache invalidation on `+test+`, which is a single-JVM
delegator.
* *The MySQL and Oracle datasource definitions are retained in full.*
`+localmysql+`, `+localmysqlolap+`, `+localmysqltenant+`, `+odbcmysql+`,
`+localoracle+` and `+localoracledd+` are all still declared in the
committed `+entityengine.xml+`, alongside the definitions for every other
database OFBiz has ever supported. Nothing was deleted to make room for
PostgreSQL. Selecting one of them is the same exercise it has always been:
point the delegator's group-maps at it and put its JDBC driver on the class
path. Only the PostgreSQL driver is *bundled*, so a MySQL or Oracle driver
goes into `+/ofbiz/lib-extra+` - see the note on that volume at the end of
_Database portability_ below.
* *The per-dialect field-type mappings are untouched.* All twelve files
under `+framework/entity/fieldtype/+` - `+fieldtypeadvantage.xml+`,
`+fieldtypeaxion.xml+`, `+fieldtypedaffodil.xml+`,
`+fieldtypefirebird.xml+`, `+fieldtypeh2.xml+`, `+fieldtypehsql.xml+`,
`+fieldtypemssql.xml+`, `+fieldtypemysql.xml+`, `+fieldtypeoracle.xml+`,
`+fieldtypepostgres.xml+`, `+fieldtypesapdb.xml+` and
`+fieldtypesybase.xml+` - are present and unmodified, as is the abstract
field-type grammar they map from. The entity model is therefore still
portable across every dialect it was portable across before, and moving
between supported majors of one database needs no field-type change at all.

===== H2

To use the embedded H2 database, ensure all database related
environment variables are unset.

"Unset" means unset, not empty. `+OFBIZ_POSTGRES_HOST+` is the only
variable that selects the managed database, so leaving it out while
supplying any other `+OFBIZ_POSTGRES_*+` variable is a contradiction -
the database name, user, password and TLS settings would all be ignored
and the container would serve traffic from an embedded H2 file on its own
volume, invisible to every other instance and destroyed with the
instance. The entry point therefore refuses to pass over that
combination:

* in the `+dev+` profile it prints a `+WARNING+` naming every variable
  that will have no effect and continues on the embedded database, so the
  local workflow of leaving a database block in a compose file with the
  host commented out still works;
* in the `+prod+` profile it fails the start, because an instance that
  serves real traffic must not fall back to an embedded database;
* an `+OFBIZ_POSTGRES_*+` variable supplied with an *empty* value fails
  the start in *either* profile, and the error names each offending
  variable. An empty value is what an unresolved secret reference or an
  unrendered template leaves behind, so it is never read as a request for
  the default in the tables below. Without that rule an empty
  `+OFBIZ_POSTGRES_OFBIZ_DB+` became the literal default `+ofbiz+` and
  the only symptom was the driver's own
  `+database "ofbiz" does not exist+` much later, from inside the entity
  engine.

*`+OFBIZ_PROFILE=prod+` requires an external database, whether or not any
database variable was supplied.* The rules above are about a configuration
that lost a variable; this one is about a container that was given none. A
`+prod+` start whose effective configuration maps an entity group of the
`+default+` delegator to an embedded database fails, naming each mapping
that does:

....
ERROR: OFBIZ_PROFILE=prod but the 'default' delegator of
framework/entity/config/entityengine.xml maps entity group(s) to an
embedded database that lives on this container own filesystem:
org.apache.ofbiz->localh2 org.apache.ofbiz.olap->localh2olap
org.apache.ofbiz.tenant->localh2tenant.
....

Without it, `+OFBIZ_PROFILE=prod+` on its own - every secret supplied, no
database configured - started, reported itself healthy to the load
balancer, and served each request from an H2 file on whichever instance
received it. Three things satisfy the check, and the error names all
three: set `+OFBIZ_POSTGRES_HOST+` with the variables below; mount your
own configuration pointing at an external database, as _Another database,
or a configuration of your own_ describes; or say the run is a
development one with `+OFBIZ_PROFILE=dev+`, which is untouched by this
check and still boots on H2 with nothing configured.

What counts as external is the JDBC URI of each datasource the `+default+`
delegator maps, read from the configuration the instance will actually
load. `+jdbc:h2:file:+`, `+jdbc:h2:mem:+`, a local `+jdbc:derby:+`, a
`+jdbc:hsqldb:file:+` or `+mem:+` and `+jdbc:sqlite:+` are embedded and
refused; every network URI is accepted, `+jdbc:h2:tcp:+` and
`+jdbc:derby://+` included, because those are reached over a socket and
shared. A mapping whose datasource the file does not declare, or a
datasource declaring neither an `+inline-jdbc+` URI nor a
`+jndi-jdbc+` reference, is also refused: the `+prod+` profile does not
assume that a database it cannot identify is a shared one.

===== Another database, or a configuration of your own

MySQL, Oracle and the other dialects OFBiz supports are not configured
through environment variables - only H2 and PostgreSQL are - and neither
is a PostgreSQL that needs a JDBC parameter the template below does not
carry. For those, supply the entity configuration itself: mount your own
`+entityengine.xml+` at `+/ofbiz/config/entityengine.xml+` and leave
`+OFBIZ_POSTGRES_HOST+` and `+OFBIZ_DISTRIBUTED_CACHE_CLEAR+` unset.
`+/ofbiz/config+` precedes `+ofbiz.jar+` on the class path, so that file -
and not the committed one - is what the Entity Engine reads. The committed
`+framework/entity/config/entityengine.xml+` is the starting point to copy
and edit: it already declares `+localmysql+`, `+localoracle+` and the
other dialect datasources together with their field-type mappings, so in
most cases the edit is repointing the `+group-map+` elements of the
`+default+` and `+default-no-eca+` delegators. Put the JDBC driver in
`+/ofbiz/lib-extra+`, which precedes the bundled `+/ofbiz/lib+`.

*That file is yours, and the container does not touch it.* Every
`+entityengine.xml+` the entry point renders carries an
`+OFBIZ-CONTAINER-GENERATED-ENTITY-ENGINE-CONFIGURATION+` comment as its
first line after the XML declaration, and that marker is the only thing
that lets the entry point replace or delete the file at that path:

* a file *without* the marker is never overwritten and never removed. This
  is what makes the paragraph above true rather than a trap - leaving
  `+OFBIZ_POSTGRES_HOST+` unset is also what selects the mode whose job is
  to delete a stale render, and before the marker existed that deletion
  took the mounted file with it and silently started the fleet on the
  committed embedded H2 configuration;
* setting `+OFBIZ_POSTGRES_HOST+` or `+OFBIZ_DISTRIBUTED_CACHE_CLEAR+`
  while such a file is present is *refused*, before anything is written,
  rather than resolved by overwriting it. Both are ways of asking the
  container to own the configuration, and the container renders from the
  pristine source, so it could not put your file back. To run your own
  configuration with cross-instance invalidation, set
  `+distributed-cache-clear-enabled="true"+` on the `+default+` and
  `+default-no-eca+` delegators of your own file - and supply the
  `+OFBIZ_JMS_*+` transport, which is independent of this;
* a file *with* the marker is the container's own render and is replaced
  on every start and removed when the variables are withdrawn, which is
  what makes "unset the variable" undo the configuration it set;
* a file with no marker sitting beside a container state record written by
  an image *older* than the marker convention is recognised as that older
  image's render and is withdrawn, so an existing deployment upgrades
  without a refused start. It is announced when it happens. Only that
  case is inferred; a file beside a current state record is treated as
  yours.

Keeping your file is not the same as trusting it. Two things are still
checked on whichever configuration is authoritative, and both fail the
start rather than being reported and passed over:

* its managed datasources may not leave startup DDL enabled - see
  _Schema initialization_ - so a mounted file cannot reintroduce
  per-boot DDL across the fleet;
* in `+OFBIZ_PROFILE=prod+`, every datasource the `+default+` delegator
  maps must be an external database, exactly as described under _H2_
  above.

====== Schema initialization

A serving instance issues no DDL. The three managed datasources are
rendered with `+check-on-start="false"+` and
`+add-missing-on-start="false"+`, so the account a running container
connects with needs no schema privileges at all, and a fleet that scales
out cannot have two instances altering the same table at the same time.

Schema changes are applied by running the image once, to completion, with
the same configuration a serving instance is given plus
`+OFBIZ_SCHEMA_INIT=true+`:

[source,shell script]
----
docker run --rm --env OFBIZ_PROFILE=prod --env OFBIZ_SCHEMA_INIT=true \
    --env-file ofbiz-postgres.env --env-file ofbiz-secrets.env \
    --env-file ofbiz-postgres-init.env ofbiz-docker
----

The init execution renders the *same* configuration files as a serving
instance, so under `+OFBIZ_PROFILE=prod+` it needs the same three secrets
described in the _Secrets_ section as well as the database credentials.
Give it the same secret source the serving instances use rather than a
second set of values.

The one thing it is given that a serving instance is *not* is the
schema-initialization database identity - the
`+ofbiz-postgres-init.env+` file above, holding the six
`+OFBIZ_POSTGRES_*_INIT_*+` variables. Under `+OFBIZ_PROFILE=prod+` that
file is required by an init execution and *refused* for a serving one, so
the split into two files is not a convention you have to remember: a
manifest that gives the fleet the privileged credential is rejected, and
so is an init job that was not given it. See _Database roles and least
privilege_ below.

That execution renders both flags as `+true+` and then lets the entity
engine create every missing table, column, index and key from the entity
model. It does that through a data load - `+--load-data readers=none+`,
naming a reader no component declares - because the engine has no
standalone DDL command: constructing the delegator is what performs the
startup database check, so the whole schema is applied while no seed data,
no demo data and no administrative user are loaded. It is not entirely
free of DML, and the distinction is worth drawing precisely: the loader
upserts one `+Component+` row per loaded component before it resolves a
reader, which the engine's own `+0 rows changed+` report does not count.
That is bookkeeping about which components were seen, not business data.
It then
verifies the result against the database, and then exits `+0+` without
serving traffic. Run it as an init container or a job before the first
release of a schema-affecting change, with a database account that may
issue DDL; the serving instances keep using an account that may not. The
DDL is additive - the engine creates what is missing and never drops - so
re-running it is harmless, and each run reports whether this container has
initialised this same target before, naming what changed when it has not.

It applies the schema and nothing else. `+OFBIZ_DATA_LOAD+` is *ignored*
for this execution and no administrative user is created; a value other
than `+none+` is reported as ignored rather than silently dropped. Note
that an *unset* `+OFBIZ_DATA_LOAD+` resolves to `+seed+`, so an init
execution that says nothing about it is reported as ignoring `+seed+` on
every start. Set `+OFBIZ_DATA_LOAD=none+` on an init execution to
acknowledge that it loads nothing, which is what keeps that warning for the
case it is meant for - a manifest that really did ask this execution to
load data. It is
also independent of the first-run flags in
`+/ofbiz/runtime/container_state+`, so a schema change can be applied to
a container whose data has already been loaded.

Bringing up a *fresh* managed database therefore takes three steps, in
this order:

. *Apply the schema* with the one-shot execution above. It exits `+0+` and
serves nothing. This is the only step that is given the
`+ofbiz-postgres-init.env+` identity.
. *Load the data once*, with `+OFBIZ_SCHEMA_INIT+` unset, `+OFBIZ_DATA_LOAD+`
naming the tier and the *serving* database identity - a data load is pure
DML and needs no DDL privilege. See _Loading data_ below for the whole of
that step, including the administrative user it creates.
+
[source,shell script]
----
docker run --rm --env OFBIZ_PROFILE=prod --env OFBIZ_DATA_LOAD=demo \
    --env OFBIZ_ADMIN_USER=admin \
    --env-file ofbiz-postgres.env --env-file ofbiz-secrets.env \
    ofbiz-docker /bin/true
----
. *Start the serving instances.* `+OFBIZ_SCHEMA_INIT+` stays unset, so
`+check-on-start+` and `+add-missing-on-start+` render as `+false+` and no
serving instance issues DDL, and `+OFBIZ_SKIP_INIT=true+` says the database
is already populated. Each instance is given the *serving* database
identity, the same three secrets, and a route id of its own.
+
[source,shell script]
----
docker run --detach --publish 8443:8443 \
    --env OFBIZ_PROFILE=prod --env OFBIZ_SKIP_INIT=true \
    --env OFBIZ_JVM_ROUTE=instance-a \
    --env-file ofbiz-postgres.env --env-file ofbiz-secrets.env \
    ofbiz-docker
----

A later release that changes the entity model repeats step 1 only. The DDL
is additive, so applying it to a populated database creates what is missing
and leaves the data - and the running fleet, until it is rolled - alone.

Treat a non-zero exit as "the schema was not applied" and do not release
on top of it. The exit status is trustworthy in that direction because it
does not rely on the data loader's own: `+--load-data+` returns `+0+` even
when it could not reach the database and abandoned the check, and it also
returns `+0+` when the check ran but individual `+CREATE TABLE+` or
`+ALTER TABLE+` statements were refused - the entity engine logs such a
failure and carries on with the next entity. Either case would otherwise
report success for a database with some tables and not others.

The init execution therefore runs in *two passes*:

. *Apply.* Both flags are `+true+`. The entity engine creates everything
the entity model declares that the database does not have. The pass fails
if the loader exits non-zero, if the engine never reported performing the
startup database check, if it abandoned the check, or if it reported that
any individual DDL statement failed.
. *Verify.* The same invocation is repeated against the same
configuration with `+add-missing-on-start+` rewritten to `+false+`, so the
engine compares the entity model against the live catalogue and issues no
DDL at all - it cannot repair what it finds, only report it. The pass
fails if the engine still reports a table or a column as missing, if it
reports a column whose *type, width or scale* is not the one the model
declares, if it reports a *column the model has no field for*, or if it did
not re-read every entity group the first pass wrote to.

*Present is not the same as correct*, which is why the second and third of
those exist. A column of the wrong type, width or scale is a schema the
engine's generated SQL cannot use correctly - it fails at run time, or
silently truncates - and re-running the init job does not repair it, because
the DDL is additive and never alters an existing column. Such a schema is
refused with no way to override it. A column the model has no field for is
different: it is harmless when it is nullable or has a default, and it
breaks *every* insert into its table when it is `+NOT NULL+` without one.
The engine reads each column's nullability and never reports it, so this job
cannot tell those two apart and refuses rather than guess -
`+OFBIZ_SCHEMA_INIT_ACCEPT_EXISTING=true+` is how an operator states that
the difference is deliberate, which it usually is for a field an upgrade
withdrew.

There is also a third question, and it is the one no comparison can answer.
Three properties of a table are invisible to this job: the nullability and
defaults of its columns, which the engine reads and never reports, and its
primary keys, foreign keys and indexes, whose comparison reads *nothing at
all* on PostgreSQL - the engine creates objects with unquoted upper-case
names, which PostgreSQL folds to lower case, and then looks the metadata up
in upper case. Measured on a full initialization against PostgreSQL 13.23:
the engine logged `+Reviewed 0 primary key fields from database.+` and
`+There are 0 indices in the database+`, and reported 1691 primary keys and
1970 foreign keys as missing, against a database holding 852 primary key
constraints, 1970 foreign key constraints and 4600 indexes that the *same
run* had just created. None of those reports can therefore be treated as
evidence; doing so would fail every correct initialization.

What replaces them is stronger than a comparison: *the job proves it created
the schema itself*. It compares three numbers the engine publishes - the
entity count `+ModelReader+` logs, the number of entities it found without a
table, and the number of tables it created - and when all three agree, every
table was created from the entity model in that execution, so the
nullability, the defaults, the primary keys, the foreign keys and the indexes
are the model's by construction and need no reading back. When they do not
agree, the schema was partly there already, and the job refuses with the
three numbers in the message rather than releasing a fleet onto a schema it
cannot vouch for. Re-initializing an existing schema is a legitimate
operation - it is how a schema-affecting upgrade is applied - so
`+OFBIZ_SCHEMA_INIT_ACCEPT_EXISTING=true+` accepts those three unproved
properties, and the closing log line then states precisely which of them
were *not* established. Against a database that should have been empty,
treat the numbers as the finding: something else has already written to it.

Only when both passes are clean is the target recorded in
`+/ofbiz/runtime/container_state/schema_initialised+` and
`+Schema applied and verified against the database+` printed. A failure
names the engine message that caused it, so the cause - most often a
database account without rights to create every object - is visible in the
same output. The verification pass creates nothing, so it is safe to
repeat, and the configuration the first pass used is put back afterwards on
every path, including a failing one. That last step is not housekeeping:
`+/ofbiz/config+` is normally a persistent volume, so a DDL-enabled file
left behind would outlive the job and be read by the next container that
mounted the volume.

The cost is a second JVM start up. For a one-shot job that gates a fleet
roll-out that is the intended trade: the alternative is releasing onto a
half-created schema.

*Run exactly one of these at a time.* Two concurrent init executions issue
the same `+CREATE+` and `+ALTER+` statements against one catalogue: they
contend on catalogue locks, and each engine reports as *failed* every object
the other created first. Both would then exit non-zero on a schema that is
actually complete, so neither exit status means what an orchestrator reads it
to mean. Nothing about the DDL is damaged - it is additive either way - but
the gate stops working, which is worse than a slow one.

Two things guard against it, and it matters which is which:

* the container takes a *kernel lock* on
  `+/ofbiz/runtime/container_state/schema_init.lock+` for the whole init
  execution, and *refuses immediately* rather than waiting when another
  holder has it, naming that holder. It refuses rather than queues on
  purpose: waiting and then re-applying the same additive DDL would succeed
  and thereby *hide* the orchestration fault. The lock is released when the
  holder exits for any reason, including being killed, so it leaves nothing
  stale behind, and the lock file itself is deliberately never deleted
  because it *is* the lock's identity;
* `+OFBIZ_SCHEMA_INIT_SINGLETON_ACKNOWLEDGED=true+` is required in the
  _prod_ profile, and it is required *because of the lock's limit*. A kernel
  lock only sees executions that share the file - which means the same
  `+/ofbiz/runtime+` volume. It cannot see a second execution on another host
  or with its own volume, which is exactly the shape an orchestrator produces.
  The acknowledgement is where an operator states that the orchestrator, which
  can see them all, runs one.

There is no database-side advisory lock, and that is a deliberate choice
rather than an omission: the runtime image carries no database client, such a
lock would have to be held by a long-lived connection across a JVM this entry
point only supervises, and it would work for PostgreSQL alone while the
datasource definitions have to stay portable.

The one operational consequence of reading the log is that the check needs
it: an image configured to suppress `+info+` logging fails closed here,
reporting that the check was not observed rather than claiming a schema it
cannot confirm.

Applying the schema is its own step, taken before any data is loaded, and
it is deliberately *not* governed by the
`+/ofbiz/runtime/container_state+` flags that make the other
initialization steps run only once. Those flags record what a particular
container's state volume has already done, whereas the schema is a
property of the database, so an init execution pointed at a *new*
database must still apply the DDL even when it is handed a state volume a
previous container wrote.

What that state volume remembers about the database is recorded in
`+/ofbiz/runtime/container_state/db_config_applied+`. The record is a
versioned, non-secret fingerprint of the entity engine configuration the
start applied: the profile, the database mode, the schema mode and the
cache-invalidation flag, and - for a managed database - the host and port,
the three database names, the three user names that were actually rendered
and whether those were the serving or the initialization identity, the TLS
settings, the pgJDBC network deadlines and the connection-pool sizing. No
password is included, so rotating one is not reported as a changed target,
and does not need to be: the configuration is re-rendered on every start
regardless of what the record says. It is read back, and not merely
written, on every start that configures a managed database - that is,
whenever `+OFBIZ_POSTGRES_HOST+` is set and `+OFBIZ_SKIP_INIT+` is not -
and what differs is reported by field *name*, never by value, so the log
identifies what moved without becoming an inventory of the deployment.

The comparison is a diagnostic and never decides whether to render, so a
corrupt, empty or earlier-format record can cost a log line and nothing
more. Two changes are worth knowing about when a volume outlives the
container that wrote it:

* a *changed database* - a different host, port, database name or user name
- means the `+data_loaded+` and `+admin_loaded+` markers were written for
another deployment. They are disbelieved for the reason given in
_Container runtime options_ above, because each marker body embeds that
same structural identity, so a container pointed at a freshly provisioned
database re-evaluates the data and admin loads instead of skipping them and
coming up against an empty schema with no seed data and no way to log in.
The record is what names the fields that changed, which is what makes the
reason visible rather than leaving a re-run to be puzzled over;
* a *changed schema mode* against the same database discards nothing - the
data is still there - but is reported, and the record is refreshed to the
new mode. A serving container that has become an init job, or an init job
that has become a serving container, is the transition most worth seeing
in a log, and an init run applies its DDL regardless of any flag, so
nothing has to be removed for it to do its work.

A record written in an earlier format - an image that wrote a bare host
name, or one that recorded fewer fields - is not comparable with one
written now and is replaced rather than compared field by field. That is
reported too, and again discards no load state; delete
`+/ofbiz/runtime/container_state+` yourself if that volume was last used
against a different database.

An init execution reports success only once the schema has been verified
to be there, because an orchestrator reads `+0+` from an init container
as permission to start the fleet. It therefore runs the entity engine
twice against the same database. The first pass applies the DDL. The
second repeats the database check over the schema the first one created
and has to find nothing left to create; it is the pass that turns "the
loader exited zero" into "the schema is really there". Both passes must
in addition show, in their own output, that every managed datasource the
`+default+` delegator resolves to was initialized, and that a database
check really ran with `+addMissing+` enabled - a configuration
accidentally rendered in run mode constructs the datasources, checks
nothing and exits `+0+`. Neither pass may report a connection it could
not establish, a table, column or schema enquiry it had to abort, or a
column it could not add: the entity engine logs each of those and
carries on, leaving the exit status at `+0+`. A loader that exits
non-zero fails the step as well, so a database that cannot be reached is
reported rather than assumed.

The verification pass is what makes a missing DDL privilege visible. The
entity engine logs a `+Could not create+` error for each object it is
refused, continues, and still exits `+0+`, so the DDL pass on its own
cannot tell you whether the account was allowed to do the work. The
second pass finds those tables still absent and fails the run. If an
init execution fails this way, search its log for
`+has no table in the database+` to see which entities are missing and
for `+Could not create+` to see why - almost always a role without DDL
rights. This is the check that stops a partly created schema from being
handed to the fleet as though it were complete.

A first initialization against an empty database legitimately reports
every table as missing, in those same words, while it is busy creating
them. That is why only the second pass treats the report as a failure.

The schema truth stays the entity model: no Flyway, Liquibase,
schema-version table, or hand-written DDL is introduced. A change to an
`+*-entitymodel.xml+` file is the whole change, and this initialization run
is what applies it.

An orchestrator reads that exit `+0+` as permission to start the fleet, so
four guard rails make it trustworthy.

`+OFBIZ_SCHEMA_INIT=true+` combined with `+OFBIZ_SKIP_INIT=true+` is
refused: the entity engine has no standalone DDL command - the schema is
applied when the data loader creates a delegator - so the data load *is*
the schema application, and skipping it would exit successfully having
created nothing.

The DDL pass runs even when
`+/ofbiz/runtime/container_state/data_loaded+` already exists. That marker
records that data was loaded at some point in the *state volume's* life,
not that the database this execution is pointed at has any tables - repoint
a reused volume at a fresh managed database and the marker is still there -
so it is ignored for the schema, and only for the schema. No data is
loaded, so an already populated database is not touched.

An init execution will not report success unless a schema-applying data
load actually ran and finished during that execution *and* the completeness
verification against the database then came back clean. Neither half can be
supplied from outside: the fact that the loader ran is recorded by the very
lines that execute it, not read from the environment or from a volume, and
the other half is a question put to the database. An init job whose loader
failed, or that was killed part way through, therefore exits non-zero.

On success the override is re-rendered with startup DDL disabled *before*
the exit. `+/ofbiz/config+` is a volume that outlives the container, so
without that step an init job would hand the fleet a configuration with
both flags still `+true+` - and the first serving instance to read it
would issue DDL after all.

Independently of the mode, and on *every* path including
`+OFBIZ_SKIP_INIT+`, the installed configuration is read for what it *is*
and a serving start up is refused unless every non-embedded datasource it
serves from states both DDL flags off. What is required is the exact posture
run mode is defined by - `+check-on-start="false"+` *and*
`+add-missing-on-start="false"+`, both present, both that literal - and
anything else is refused with a message naming which of the two is wrong.
The gate refuses rather than repairs, because the file may have been
provisioned by an operator rather than rendered here.

It deliberately does not settle for "as it happens, no DDL would be issued
right now", because two postures pass that weaker test and neither is safe
to serve from:

* an *absent* `+check-on-start+` reads as *enabled*: the engine resolves
  the attribute as `+!"false".equals(value)+`, so a missing attribute, an
  empty one and an unsubstituted placeholder all leave the startup schema
  check on. Every instance then reads the whole schema on every boot, needing
  metadata privileges the fleet is meant not to hold, and the file never
  states its posture - so "this deployment decided not to issue DDL" is
  indistinguishable from "nobody considered it";
* `+add-missing-on-start="true"+` beneath a correct
  `+check-on-start="false"+` issues nothing *today*, only because the engine
  consults the second flag solely when the first is enabled. It is a declared
  intent to create and alter objects, one edit or one re-render of the first
  flag away from a whole fleet doing so.

Both are therefore refused at start up, where an operator can still correct
the file, rather than discovered when a fleet member creates a table.

Which datasources are judged is derived from the configuration's own
`+default+` and `+default-no-eca+` `+group-map+` entries rather than from a
fixed list of names, so a configuration that serves from datasources of its
own naming - a mounted MySQL or Oracle file, which stays selectable - is
held to the same posture as a rendered PostgreSQL one. The `+test+`
delegator is deliberately not read; it is single-JVM dev and test only.
Attribute spellings XML permits are normalised before they are matched -
whitespace around the `+=+` and single quotes - so a hand-written file is
judged on its posture rather than on its punctuation, and only the start tag
is read, so no credential is examined.

The refusal names whose file it is, because the two are corrected in
different places: a *rendered override* is fixed by supplying the
`+OFBIZ_POSTGRES_*+` variables or by deleting
`+/ofbiz/config/entityengine.xml+` so the committed configuration applies,
whereas an *entity engine configuration supplied by this deployment* - an
unmarked file an operator mounted - can only be corrected by its author, and
the message asks for the two attributes rather than offering to re-render
it. Ownership is read from the generated-file marker in the first few lines
of the override, so neither a large mounted file nor a comment further down
that mentions the marker can misattribute it. A datasource a serving
delegator maps but that the file does not define carries no posture to read
and is left to the prod-profile external-datasource check; a file from which
no `+group-map+` can be read at all is reported as a warning naming what to
check, since refusing a configuration whose delegators could not be parsed
would fail the local run as well.

After rendering the configuration the container also
re-reads it and refuses to start unless all three managed datasources agree
on the requested mode *and* authenticate as the identity that was resolved
for that mode, so an out-of-date copy of
`+docker/templates/postgres-entityengine.xml+` cannot leave a serving
instance issuing DDL, nor an init execution issuing none, nor either of
them connecting as the wrong role. That check inspects the file OFBiz will
actually read, whoever wrote it, and it runs even when `+OFBIZ_SKIP_INIT+`
is set.

Only the managed datasources are gated. The embedded H2 datasources keep
both flags enabled, which is what makes a zero-configuration local run
work; H2 is never part of a multi-instance fleet.

====== Loading data

*A first deployment needs a second preparation run, before the fleet
starts.* On an empty database the schema initialization leaves a complete
set of tables with no seed data and no login, so a serving instance started
with `+OFBIZ_SKIP_INIT=true+` on top of it comes up unable to authenticate
anybody. Load the data with its own execution that does *not* set
`+OFBIZ_SCHEMA_INIT+`, giving it `+OFBIZ_DATA_LOAD+` and the *serving*
credentials - a data load is `+INSERT+`, `+UPDATE+` and `+DELETE+` on
tables that already exist, so it needs no DDL privilege, and under
`+OFBIZ_PROFILE=prod+` the initialization identity is refused for any
execution that is not the schema init:

[source,shell script]
----
docker run --rm --env OFBIZ_PROFILE=prod --env OFBIZ_DATA_LOAD=demo \
    --env OFBIZ_ADMIN_USER=admin \
    --env-file ofbiz-postgres.env --env-file ofbiz-secrets.env \
    ofbiz-docker /bin/true
----

This is the execution that creates the administrative user, so it is the
one that needs `+OFBIZ_ADMIN_USER+` and `+OFBIZ_ADMIN_PASSWORD+` - the
latter from the same secret source as the other credentials, and required
outright under `+OFBIZ_PROFILE=prod+`. Setting either of them on a serving
instance has no effect, because `+OFBIZ_SKIP_INIT+` makes them ineffective.

The trailing `+/bin/true+` is what makes it a job rather than a server. The
entry point performs the whole initialization and then executes whatever
command it was given, so replacing the image's default `+bin/ofbiz+`
command makes the container exit `+0+` as soon as the load and the
administrative user are in place. Run it once per database, after the
schema initialization and before the first serving instance; every serving
instance then runs with `+OFBIZ_SKIP_INIT=true+`, which is also what keeps
a fleet from having several instances load the same data at once. Wire the
three executions together in whatever orchestrator you deploy with - two
one-shot jobs followed by the serving service - and make the serving
service depend on both having exited `+0+`.

Either data tier is enough for a routable fleet. Readiness asks the
database a question whose answer it does not read - see _Health and
readiness endpoints_ above - so a `+seed+`-loaded database is reported ready
exactly as a `+demo+`-loaded one is, and no first sequenced write has to be
arranged before the instances are registered with a target group.

====== Database roles and least privilege

Rendering `+check-on-start="false"+` and `+add-missing-on-start="false"+`
stops a serving instance from *issuing* DDL. It does not take the
*ability* away: if the fleet authenticates as the same account the init
job used, then every serving instance still holds the privilege to
create, alter and drop tables, and anything that can reach one of those
instances or read the credential out of its environment inherits it. The
two are separated, so that the privilege lives only where the process
that holds it is short lived, runs once, and serves no traffic.

Give each of the three databases *two* accounts:

* a *schema-initialization role* that owns the database and its schema
and may therefore create, alter and drop objects, used only by the
`+OFBIZ_SCHEMA_INIT=true+` execution; and
* a *serving role* that may read and write rows but may not create,
alter or drop anything, used by every instance that serves traffic.

The entry point selects between them. An execution with
`+OFBIZ_SCHEMA_INIT=true+` renders the six `+OFBIZ_POSTGRES_*_INIT_*+`
values into the three managed datasources; every other execution renders
the serving credentials. The rules are enforced rather than documented:

* All six init variables must be supplied together. Five of six is
refused, naming the count, because a partial identity would silently
leave one database being initialized by its serving role.
* Each init role name must differ from *all three* serving role names,
and each init password from all three serving passwords. An '`init`'
identity that is really the serving one is refused, which is what stops
the separation being defeated by copying the values across.
* Under `+OFBIZ_PROFILE=prod+` the init identity is *required* for an
init execution and *refused* for a serving one. Under `+dev+` both cases
warn and fall back to the serving identity, so a single-host local run
still works with one set of credentials.
* The rendered file is re-read, and the start up fails unless each
managed datasource carries the role that was resolved for the mode.

The three init passwords are treated exactly like the other secrets: they
are written only into the mode 0600 rendered
`+/ofbiz/config/entityengine.xml+`, are hidden from any tracing, are
removed from the environment of every hook script, and are removed from
the environment before OFBiz is started.

The grants below create that pair for the _ofbiz_ database. Run them as a
superuser, once per database, substituting the olap and tenant names for
the other two. `+public+` is the schema OFBiz uses - the managed
datasources are rendered with `+schema-name="public"+`.

[source,sql]
----
-- The two accounts. Only the first one will ever hold DDL privileges.
CREATE ROLE ofbiz_init LOGIN PASSWORD 'the-init-password';
CREATE ROLE ofbiz_app  LOGIN PASSWORD 'the-serving-password';

-- Owned by the init role, so the init execution can create and alter
-- objects without any explicit grant, and nobody else can.
CREATE DATABASE ofbizmaindb OWNER ofbiz_init;

-- PUBLIC can connect to any database and create temporary objects in it
-- unless told otherwise, so say otherwise, then grant back only what is
-- needed. CONNECT lets a role open a session. TEMPORARY is kept so the
-- revoke changes nothing that worked before; it permits session-local
-- objects only, which cannot alter the persistent schema. Drop it if you
-- want the tighter grant.
REVOKE ALL ON DATABASE ofbizmaindb FROM PUBLIC;
GRANT CONNECT, TEMPORARY ON DATABASE ofbizmaindb TO ofbiz_init;
GRANT CONNECT, TEMPORARY ON DATABASE ofbizmaindb TO ofbiz_app;

-- The remaining statements act on objects inside the database, so they
-- must be run while connected to it: \c ofbizmaindb
\connect ofbizmaindb

-- Before PostgreSQL 15, every role may create objects in "public". That
-- would hand the serving role the DDL this whole arrangement removes.
ALTER SCHEMA public OWNER TO ofbiz_init;
REVOKE ALL ON SCHEMA public FROM PUBLIC;
GRANT USAGE ON SCHEMA public TO ofbiz_app;

-- Rows yes, tables no. USAGE without CREATE lets the serving role reach
-- objects in the schema but not add, rename or drop any.
ALTER DEFAULT PRIVILEGES FOR ROLE ofbiz_init IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO ofbiz_app;
ALTER DEFAULT PRIVILEGES FOR ROLE ofbiz_init IN SCHEMA public
    GRANT USAGE, SELECT, UPDATE ON SEQUENCES TO ofbiz_app;

-- ALTER DEFAULT PRIVILEGES applies to objects created after it runs,
-- which is the normal case here because the schema is created by the
-- init execution afterwards. These two cover a database that already
-- has tables, so the same script is correct on a second run.
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public
    TO ofbiz_app;
GRANT USAGE, SELECT, UPDATE ON ALL SEQUENCES IN SCHEMA public
    TO ofbiz_app;
----

`+ALTER DEFAULT PRIVILEGES+` is what makes the arrangement maintainable.
The serving role is granted its row privileges *before* the tables exist,
so the next schema-affecting release needs no follow-up grant: the init
execution creates the new table and the serving role can immediately read
and write it, while still being unable to create one itself.

Two things are deliberately *not* granted to the serving role. It is not
given `+CREATE+` on the database, so it cannot add a schema and work
around the restriction; and it is not made a member of the init role, so
`+SET ROLE+` cannot be used to acquire DDL. Verify the result the same way
an attacker would test it - as the serving role, `+CREATE TABLE t (i
int)+` must fail with a permission error while
`+INSERT INTO "SequenceValueItem" ...+` succeeds.

Apply the same pair to the olap and tenant databases, and keep the
separation across the three executions of _Schema initialization_ and
_Loading data_ above: the one-shot init execution gets the privileged
credential, the one-shot data load does not - a data load is pure DML and
needs no DDL privilege - and no serving instance does either.

The grant sequence is the deployment's own to apply and to verify: the
privileges of a database this image connects to live outside the image, so
nothing in the build can assert them. Verify them against the server the
fleet will actually use, with the two statements above, as part of
provisioning it - and re-verify after any change to the roles, because a
serving role that silently regains `+CREATE+` removes the only thing
standing between a mis-set `+check-on-start+` and a fleet issuing DDL.

====== Connection pools

`+OFBIZ_DB_POOL_MIN+` and `+OFBIZ_DB_POOL_MAX+` size each managed
datasource's DBCP pool, defaulting to the committed 2 and 250. Both
bounds are validated as plain integers between 1 and 10000 and a minimum
above the maximum is refused, so a mistyped value fails the start up
instead of producing a pool that cannot serve.

The default maximum long predates containers and is generous: it is a
per-instance, per-datasource bound, so _n_ instances can open up to
_n_ x 3 x `+OFBIZ_DB_POOL_MAX+` connections while PostgreSQL's own
`+max_connections+` defaults to 100. Lower it when scaling out, or put a
connection proxy in front of the database, rather than discovering the
ceiling under load.

`+OFBIZ_DB_FLEET_SIZE+` and `+OFBIZ_DB_MAX_CONNECTIONS+` have that
arithmetic checked at start up, and *both are required in the _prod_
profile*. The container refuses to start when _fleet size_ x 3 x
`+OFBIZ_DB_POOL_MAX+` could exhaust the server's `+max_connections+`, and it
reports the aggregate demand it computed even when it fits, so the number is
in the log of every start rather than only of a failing one.

They are mandatory rather than optional because the optional form was
unreachable in practice: the fleet size defaults to 1, so a deployment that
supplied neither had the check pass on the arithmetic for a single instance
while six instances of the same manifest would demand 6 x 3 x 250 = 4500
connections. A number an operator has to state is the only version of this
check that runs for the deployment that actually exists.

*Fitting is not headroom.* When the demand fits but takes more than 75% of
the usable budget, the start warns. A rolling deployment briefly running one
extra instance, a concurrent init execution and an operator's own psql session
all come out of the difference, so a fleet sized to 99% of `+max_connections+`
is one deploy away from `+FATAL: sorry, too many clients already+`. Neither
variable changes a pool: they turn a capacity mistake into a refused start,
and a tight one into a warning, rather than into that error on the instance
that happens to scale out last.

In the _dev_ profile both remain optional; a development start that supplies
neither says so and skips the check.

`+OFBIZ_DB_POOL_WAIT+` is how long a thread waits for a connection once
the pool is exhausted, and it is deliberately not left at the entity
engine's default. That default is 300000 milliseconds, so an exhausted pool
parks every request thread for five minutes: the instance stops serving,
holds its threads, and still answers a liveness check, which is
indistinguishable to a load balancer from an instance that is merely busy.
20000 milliseconds fails the borrow while the balancer's own timeouts are
still meaningful, which is what lets readiness report the instance and the
target group drain it. Raise it only if a legitimate burst really does
queue for longer than that.

Connections are validated with `+SELECT 1+` while idle in the pool, so a
connection severed by the database, a NAT gateway or a proxy is discarded
rather than handed out. Validating on *borrow* as well costs a round trip
per borrow and is off unless `+OFBIZ_DB_POOL_TEST_ON_BORROW=true+`.

====== Connection deadlines

Every managed datasource's JDBC URI carries explicit pgJDBC deadlines. Two
of them the driver leaves *unbounded*, and those are the ones that matter
most here: `+socketTimeout+` and `+loginTimeout+` both default to `+0+`,
which disables them, so an instance whose database becomes unreachable
*after* the TCP connection was established - a dropped route, a silently
severed connection, a server that accepts the connection and never replies -
keeps its request threads blocked in a read that has no end. Two others do
have an upstream bound already, `+connectTimeout+` and
`+cancelSignalTimeout+`, each defaulting to 10 seconds; the container writes
those out explicitly rather than inheriting them, so that the whole set of
deadlines is visible in one place and none of them can move under the
deployment when the driver is upgraded. One more, `+tcpKeepAlive+`, is
turned on where the driver leaves it off.

The committed values, and how each relates to the driver's own default:

* `+OFBIZ_POSTGRES_CONNECT_TIMEOUT+` (10 s) bounds the TCP connect. This
  matches the driver's own default of 10 seconds and is written out
  explicitly;
* `+OFBIZ_POSTGRES_LOGIN_TIMEOUT+` (30 s) bounds the whole
  connect-and-authenticate handshake, which is the one that covers TLS
  negotiation and which `+connectTimeout+` alone does not. This
  *overrides* the driver's default of `+0+`, no bound;
* `+OFBIZ_POSTGRES_SOCKET_TIMEOUT+` (60 s) bounds a read on an
  established connection, *overriding* the driver's default of `+0+`, which
  means no bound at all. This is the one to review: it must exceed the
  slowest legitimate statement the deployment issues, because the driver
  fails the statement and closes the socket when it expires. Raise it for a
  reporting datasource, rather than removing the bound;
* `+OFBIZ_POSTGRES_CANCEL_TIMEOUT+` (10 s) bounds the acknowledgement of
  a cancellation request, which travels over its own out-of-band connection
  and can therefore get stuck independently of the statement it is
  cancelling. This also matches the driver's own default of 10 seconds and
  is written out explicitly;
* `+OFBIZ_POSTGRES_QUERY_TIMEOUT+` (`+0+`) leaves the driver-imposed
  per-statement ceiling off, which is the committed behaviour; see below;
* `+OFBIZ_POSTGRES_TCP_KEEPALIVE+` (`+true+`) lets the operating system
  detect a connection that was severed without a FIN, which is what an
  idle-connection timeout in a NAT gateway or load balancer does. The
  driver's own default for `+tcpKeepAlive+` is `+false+`, so this one is an
  override too.

The connect and socket deadlines are the one pair whose ranges are *not*
independent: `+OFBIZ_POSTGRES_CONNECT_TIMEOUT+` must not exceed
`+OFBIZ_POSTGRES_SOCKET_TIMEOUT+`, and the container refuses to start when
it does, naming both values. The reason is that pgJDBC applies
`+socketTimeout+` to the reads of the start-up handshake as well, so
whichever of the two is smaller is what actually ends a connection
attempt: a connect deadline above the socket deadline is not the deadline
that would be in force, and it is refused rather than quietly reconciled.

In practice that means the two published ranges are reachable in full only
together. With the other variable left at its default, the usable values
are 1 to 60 seconds for `+OFBIZ_POSTGRES_CONNECT_TIMEOUT+` (the socket
default is 60) and 10 to 86400 seconds for
`+OFBIZ_POSTGRES_SOCKET_TIMEOUT+` (the connect default is 10). To use the
extremes - a 300 second connect deadline, or a 5 second socket deadline -
set both variables in the same run, for example
`+-e OFBIZ_POSTGRES_CONNECT_TIMEOUT=300 -e OFBIZ_POSTGRES_SOCKET_TIMEOUT=86400+`
for a very patient connect, or
`+-e OFBIZ_POSTGRES_SOCKET_TIMEOUT=5 -e OFBIZ_POSTGRES_CONNECT_TIMEOUT=1+`
for a very impatient one. No other deadline constrains another.

`+OFBIZ_POSTGRES_QUERY_TIMEOUT+` is separate and defaults to `+0+`, no
driver-imposed limit, which preserves the committed behaviour: it is a
per-statement ceiling applied by the driver to statements that set none of
their own, and a value that is too low fails legitimate long-running work
such as a data load.

After rendering the configuration the container re-reads it and refuses to
start unless every managed PostgreSQL URI carries the resolved deadlines
and every managed pool carries the resolved borrow wait, so an out-of-date
copy of `+docker/templates/postgres-entityengine.xml+` cannot quietly
restore the unbounded behaviour.

====== Database passwords

The three database passwords have no default. They previously defaulted
to `+ofbiz+`, `+ofbizolap+` and `+ofbiztenant+`, which are published in
this repository, so a deployment that omitted one authenticated with a
value anybody could look up. The container now refuses to start when a
password is missing, naming the variable, and refuses those three values
outright - together with `+postgres+` and `+password+` - in every
profile. Rotate the credentials of any database that was provisioned
with them.

When `+OFBIZ_PROFILE+` is `+prod+` a password must additionally be at
least 16 characters long and use at least eight distinct characters. The
`+dev+` profile applies no length or entropy floor, so a local database
with a short password still works. As with the secrets above, the
passwords are written only into the mode 0600 rendered
`+/ofbiz/config/entityengine.xml+`, are substituted from a temporary file
rather than a command-line argument, and are removed from the environment
before OFBiz starts.

====== Transport security

The three managed datasources connect with `+sslmode=verify-full+` by
default. That encrypts the connection, checks that the server
certificate chains to a trusted root, and checks that the hostname
matches that certificate. The weaker modes are unsafe in ways that are
easy to miss: `+prefer+`, which is the driver's own default, silently
falls back to an *unencrypted* connection when the server declines TLS;
`+allow+` and `+disable+` send the password and every entity row in
clear text; and `+require+` encrypts without authenticating the peer, so
a man in the middle can present any certificate.

`+verify-full+` is the *only* mode accepted when `+OFBIZ_PROFILE+` is
`+prod+`. `+verify-ca+` is refused there as well, which is stricter than
it first appears to need to be: it checks only that the certificate
chains to a trusted root and does *not* check that the certificate
belongs to the host that was asked for. A managed database service issues
certificates from a shared certification authority to every tenant, so
under `+verify-ca+` any other tenant's endpoint satisfies the check and
can impersonate your database - precisely the attack a verified
connection is supposed to prevent. The full driver vocabulary, including
`+verify-ca+` and the unencrypted modes, remains available in the `+dev+`
profile.

Verification needs a trusted root, and pgJDBC does not consult the JVM
trust store by default - it reads `+sslrootcert+`, which defaults to
`+${user.home}/.postgresql/root.crt+`. Either mount your provider's CA
bundle and point `+OFBIZ_POSTGRES_SSLROOTCERT+` at it, or import the CA
into the JVM trust store and add
`+sslfactory=org.postgresql.ssl.DefaultJavaSSLFactory+` to an operator
maintained copy of the render template. The certificate is not a secret,
but a deployment that cannot read it cannot verify the server.

Enforce encryption on the *server* as well, so an unencrypted client is
refused rather than quietly accepted. On a self-managed server that is a
`+hostssl+` rule in `+pg_hba.conf+`. A managed PostgreSQL service usually
exposes the same thing as a server parameter or a connection policy rather
than as an editable `+pg_hba.conf+` - look for its "require SSL" or
"enforce TLS" setting in the provider's own documentation; the setting's
name is provider-specific and no name is prescribed here. A server-side
rule cannot be forgotten the way a per-client setting can, and it covers
every client, not only OFBiz. Note that pgJDBC does *not*
read the libpq `+PGSSLMODE+` and `+PGSSLROOTCERT+` environment variables,
so setting those in the container has no effect; the two variables above
are the ones that reach the driver.

The "operator maintained copy of the render template" is a bind mount over
`+/ofbiz/templates/postgres-entityengine.xml+`, which is the file the
render reads. Editing `+/ofbiz/config/entityengine.xml+` instead does not
work *while the container renders it*: that file is then the *output* of the
render and is rewritten on every start, and `+OFBIZ_SKIP_INIT+` does not
preserve it, because the configuration is rendered before the
initialisation is skipped.

====== Supplying your own entityengine.xml instead

A deployment that needs a datasource, a pool implementation or a JDBC
parameter this image does not template can supply
`+/ofbiz/config/entityengine.xml+` itself. That file is first on the class
path, ahead of the copy inside `+ofbiz.jar+`, so what it declares is what
the engine uses.

The two modes are told apart by a marker. Every `+entityengine.xml+` the
container renders carries a
`+<!-- GENERATED BY docker-entrypoint.sh - DO NOT EDIT -->+` comment, and
the container acts only on a file that has it:

* An override *without* the marker is yours. It is never deleted, so
withdrawing `+OFBIZ_POSTGRES_HOST+` leaves your configuration in force
rather than dropping the deployment onto the committed embedded database,
and the start up says which file it left alone.
* A start that *would render* over an unmarked override is refused, naming
the file. Rendering would destroy configuration this image cannot
reproduce, so setting `+OFBIZ_POSTGRES_HOST+` or
`+OFBIZ_DISTRIBUTED_CACHE_CLEAR+` while your own override is present is
reported as the contradiction it is instead of silently resolving it.
* An override *with* the marker is the container's own previous render. It
is replaced on every start, and removed when the configuration that
produced it is withdrawn - which is what stops a decommissioned database's
host and credentials, or the DDL flags an initialization run left enabled,
from surviving into a later start.

So: set either variable and the container owns the file; leave both unset
and you own it. Do not do both.

The `+docker/examples/postgres-demo+` example runs against the stock
`+postgres+` image, which has no TLS listener, so it cannot satisfy the
`+verify-full+` default and needs `+OFBIZ_POSTGRES_SSLMODE=disable+`
supplied in the environment that runs `+docker compose up+`. It is a
single-host demo on a private compose network; do not model a deployment
that reaches its database over a network on it, and never copy that
setting into one.

====== Database portability

PostgreSQL is the *deployed* default and nothing more. Every other
datasource definition OFBiz ships is untouched and still selectable:
the committed `+framework/entity/config/entityengine.xml+` resolves the
`+default+`, `+default-no-eca+` and `+test+` delegators to the embedded
`+localh2*+` datasources, and the `+localmysql*+`, `+localoracle*+` and
the remaining definitions are all still declared beside them. So are the
twelve per-dialect mapping files in
`+framework/entity/fieldtype/fieldtype*.xml+` - `+fieldtypeh2.xml+`,
`+fieldtypemysql.xml+`, `+fieldtypeoracle.xml+`,
`+fieldtypepostgres.xml+` and the rest - which are what give the abstract
field types their SQL for each database. Nothing in this image narrows
that choice; it only changes which datasource a container reaches for when
it is handed database settings.

What is PostgreSQL-shaped is the container's *convenience layer*, not the
product underneath it. The `+OFBIZ_POSTGRES_*+` variables render the
PostgreSQL template and the bundled JDBC driver is the PostgreSQL one, and
`+/ofbiz/config/entityengine.xml+` is the entry point's own artifact - it
is rendered when a managed database or cross-instance cache invalidation is
configured and removed when neither is, so it is not a place to leave a
hand-written file. Another database is therefore selected the way it was
before this image had database variables at all: supply an
`+entityengine.xml+` whose delegator `+group-map+` elements name that
datasource in the distribution the image is built from, and add the
database's JDBC driver to `+/ofbiz/lib-extra+`. The startup-DDL gate
described under _Schema initialization_ looks the three `+localpostgres*+`
datasources up by name and passes over a datasource it does not find, so a
configuration that serves from datasources of its own naming is left to the
operator who wrote it rather than being second-guessed.

The `+test+` delegator *always* stays on embedded H2. It is H2 in the
committed configuration and the PostgreSQL template renders it as H2 too -
that mapping is verified after every render, and a rendered file that
points it anywhere else is refused. So
`+./gradlew cleanAll loadAll testIntegration+` runs against the embedded
database whatever a container is configured with, and the integration tier
needs no database server.

The PostgreSQL JDBC driver needed to access the PostgreSQL server is
bundled with the distribution, declared in `+dependencies.gradle+`. No
driver is downloaded at container start, so the container needs no
network access to a driver host and always uses the reviewed, patched
driver version shipped with the image.

The `+/ofbiz/lib-extra+` volume remains available for operators who need
to add a *different* database driver, for example for MySQL or Oracle,
whose datasource definitions are retained in full in
`+framework/entity/config/entityengine.xml+` - together with the twelve
per-dialect field-type mappings under `+framework/entity/fieldtype/+`, see
_What selecting PostgreSQL does and does not change_ above - but whose
drivers are not
bundled. `+/ofbiz/lib-extra+` takes precedence over the bundled
libraries on the classpath, so a PostgreSQL driver left in that volume
would silently shadow, and possibly downgrade, the bundled one. The
container therefore refuses to start if it finds a `+postgresql-*.jar+`
in `+/ofbiz/lib-extra+`; delete it from the volume to start
successfully.

====== Credentials of the compose example

`+docker/examples/postgres-demo+` is a *demo*, and the four passwords it
declares - the PostgreSQL superuser password in `+postgres.env+` and the
three OFBiz database passwords in `+ofbiz-postgres.env+` - are literal
values in files tracked in this repository. They are therefore public
knowledge: anybody who deploys the example unchanged is running with
credentials that are printed in the source tree. Change all four before
the example reaches anything you care about, and rotate the credentials of
any database that was ever provisioned from it.

Supply your own values instead of editing the tracked files, so nothing
new is committed. Compose interpolates `+${...}+` in `+docker-compose.yml+`
but *not* inside an `+env_file+`, so a reference written into
`+ofbiz-postgres.env+` would reach the container as literal text rather
than as the password. Either export the overrides in the shell that runs
the stack:

[source,shell script]
----
cd docker/examples/postgres-demo
export POSTGRES_PASSWORD="$(openssl rand -base64 24)"
export OFBIZ_POSTGRES_SSLMODE=disable
docker compose up
----

or write them into a local `+.env+` file next to the compose file, which
Compose reads automatically. `+.gitignore+` excludes
`+docker/examples/*/.env+`, so that file cannot be committed by accident:

[source,shell script]
----
cd docker/examples/postgres-demo
{ printf 'POSTGRES_PASSWORD=%s\n' "$(openssl rand -base64 24)"
  printf 'OFBIZ_POSTGRES_SSLMODE=disable\n'; } > .env
chmod 600 .env
docker compose up
----

The example provisions one account per database, holding
`+ALL PRIVILEGES+`, which is *not* the posture a fleet should run with. It
is a single-host demo with one OFBiz execution that both initializes and
serves, so the two identities coincide there. A deployment separates them:
follow _Database roles and least privilege_ above for the grants, and
_Schema initialization_ and _Loading data_ above for the three executions
that keep the privileged credential out of every serving instance. Each
password must satisfy the rules described in the `+Database passwords+`
section above.

==== Object storage for content

File-backed `+DataResource+` content is *read and written* through one of
three backends, chosen with `+OFBIZ_CONTENT_STORE_PROVIDER+`. The receiving
instance still writes the file its `+objectInfo+` names whichever backend is
selected, because that is what the upload validation inspects; what the
choice decides is where the durable copy lives - see _How content reaches
and leaves the object store_ below:

`+database+`::
The `+DataResource+` database columns. This is the default and the
behaviour of an unconfigured checkout, and it is the only backend that
needs no further configuration. No object store is contacted and the
bundled AWS SDK is never loaded, so a container that leaves every variable
in this group alone behaves exactly as one with no object storage
configured - including the file-backed `+DataResource+` types, which go on
resolving to this instance's own disk. That is the reason to choose one of
the other two backends for a fleet: content held in the database columns
is shared already, but content held in a file is not.

`+filesystem+`::
The instance's own `+runtime/uploads+` tree, or wherever
`+content.upload.path.prefix+` in `+content.properties+` points. Suitable for
a single instance only, or for a fleet in which every instance mounts the same
shared volume: otherwise another instance cannot read what this one wrote, and
replacing the instance loses the content. Give the container a persistent
volume for `+/ofbiz/runtime+` if you use it.

Mount that volume inside `+/ofbiz+` rather than symlinking a path in
`+/ofbiz+` out to it. This backend confines itself to `+/ofbiz+` and never
follows a symbolic link to decide what it reads or writes: content reached
through a link, or through a directory that is a link, is refused rather
than served, because a link's name says nothing about where it points and
following one is how a link planted in a content tree ends up serving
`+/etc/passwd+`. A `+runtime+` directory symlinked to `+/mnt+` is
therefore unreadable through this backend, and a `+DataResource+` whose
recorded location is reached through a link is refused with a message
naming the ancestor at fault. Content that has to live elsewhere belongs
behind a mount point, which this backend follows because the kernel, not a
link, resolves it.

`+s3+`::
An S3-compatible object store - Amazon S3, MinIO, Ceph or anything else
that speaks the same API. One client covers all of them because
`+OFBIZ_S3_ENDPOINT+` becomes the AWS SDK's `+endpointOverride+` and
`+OFBIZ_S3_PATH_STYLE+` becomes its `+forcePathStyle+`, so the store is
addressed the way it expects rather than the way Amazon S3 does. Every
instance *reads* file-backed content from the same bucket and *publishes*
every write into it, so no instance depends on a file only it happens to
hold and no upload is lost with the instance that received it - which is
what makes it the backend to use behind a load balancer. Content written
before the backend was selected is the one thing an upload cannot place
there for you and is yours to copy in once. See _How content reaches and
leaves the object store_ below for exactly which operations reach the store,
what a rollback does, and what that copy involves.

The `+s3+` provider needs a bucket and a region, and takes an endpoint, a
credential pair and an addressing style. On Amazon S3 with an instance
role - so with no credential supplied - that is:

[source,shell script]
----
docker run -it -p 8443:8443 \
    -e OFBIZ_PROFILE=prod \
    --env-file ofbiz-secrets.env \
    -e OFBIZ_CONTENT_STORE_PROVIDER=s3 \
    -e OFBIZ_S3_BUCKET=ofbiz-content \
    -e OFBIZ_S3_REGION=eu-west-2 \
    ofbiz-docker
----

and for an S3-compatible store that is not Amazon S3, reached at its own
endpoint with a static credential:

[source,shell script]
----
docker run -it -p 8443:8443 \
    -e OFBIZ_PROFILE=prod \
    --env-file ofbiz-secrets.env \
    -e OFBIZ_CONTENT_STORE_PROVIDER=s3 \
    -e OFBIZ_S3_BUCKET=ofbiz-content \
    -e OFBIZ_S3_REGION=us-east-1 \
    -e OFBIZ_S3_ENDPOINT=https://objects.example.internal:9000 \
    -e OFBIZ_S3_PATH_STYLE=true \
    ofbiz-docker
----

with `+OFBIZ_S3_ACCESS_KEY_ID+` and `+OFBIZ_S3_SECRET_ACCESS_KEY+` in
`+ofbiz-secrets.env+`.

All seven variables are rendered into `+/ofbiz/config/content.properties+`
and are then removed from the environment, exactly as the secrets in the
_Secrets_ section are: the file is written atomically with mode `+0600+`,
the values are substituted from a temporary file rather than from a
command line, and the rendered file is read back and compared with what
was supplied, so a value that `+java.util.Properties+` would parse into
something else aborts the start up instead of silently sending content to
the wrong place. The whole property file is rendered from the copy shipped
in the distribution, because an OFBiz property override replaces a
resource rather than being merged into it key by key. The `+AWS_*+`
variables are deliberately left in place for the serving process, because
they are how the SDK's own credential and retry chains are configured - but
the nine that carry a credential or a token are removed for the duration of
every hook and every initialization child, as _Hooks_ describes.

When *no* variable in this group is set, nothing is rendered at all and
the container uses the `+content.properties+` shipped in the
distribution - which selects `+database+`. That is what keeps an
unconfigured container working with no object store and no S3 credential
in sight.

Object storage has more settings than these seven, and they deliberately
have no environment variable of their own:

* `+content.store.max.object.size+` bounds what one *whole-object* read may
  hold in memory. It does not apply to streaming a document to a consumer or
  rendering one into a screen, both of which copy the bytes through as they
  arrive - so raising it is not how a deployment serves large files;
* `+content.store.local.fallback+` opens the migration mode in which a
  store *miss* may be answered from the content an instance still holds
  locally. It is consulted at exactly that point and nowhere else: the store
  holds nothing under the key and this instance does hold a file at the
  recorded path. Where the store *does* hold the object, its object is what is
  served whatever any instance has on disk, so this setting can never make one
  instance serve content another has replaced;
* `+content.store.s3.key.prefix+` places every object key under a prefix so
  one bucket can hold several deployments;
* `+content.store.s3.api.timeout.millis+` and
  `+content.store.s3.attempt.timeout.millis+` are two deadlines rather than
  one, because the first bounds the whole call - request, response headers
  and retries - and the second bounds a single attempt inside it. Both stop
  the moment the SDK hands back the response stream, so neither bounds the
  body;
* `+content.store.s3.stream.total.timeout.millis+` is what bounds the body,
  and it is a *total* bound rather than the inactivity bound a socket timeout
  gives: the clock starts when the body is handed to its caller and covers
  every read of it, so a store that dribbles one byte just inside every socket
  timeout is abandoned instead of holding a request thread, a connection and a
  pool slot indefinitely. An overrun body is aborted rather than drained, and
  the read is refused with an opaque reference the log explains; every later
  read of that body is refused the same way, so an abandoned response stays
  abandoned. It defaults to 3600000 (one hour) with an accepted range of
  1000..86400000, and there is deliberately no value meaning "no deadline" -
  an unbounded body is the condition it exists to remove. Generous on purpose:
  it bounds content of a size an uploader chose being read by a consumer whose
  speed nothing here controls, and an hour serves the 10 MiB
  `+content.store.max.object.size+` default at under 25 kbit/s;
* `+content.store.s3.max.retries+` caps retries after a failed first
  attempt. The cap is applied to the SDK's *standard* retry strategy, which
  the provider names explicitly rather than inheriting: what the SDK picks
  when nothing says otherwise is decided by `+RetryMode+`, whose default in
  this SDK line is the *legacy* strategy, so a deployment that assumed
  "standard applies by default" was getting different backoff and no
  retry-capacity throttle - which is what stops a failing store being
  retried by every request at once;
* `+content.store.s3.insecure.endpoint.allowed+` accepts a plaintext
  `+http://+` endpoint for a host that is not the loopback interface. It is
  *derived* by the container from `+OFBIZ_PROFILE+` rather than supplied, and
  is never _true_ in _prod_.

Each has a committed default every deployment can run on and none of them is
a secret. All but the last honour a `+SystemProperty+` row - so a variable for
one would add nothing but a second place for the two layers to disagree - and
the last is read from the property file alone, for the reason given below it.

*When such an override takes effect is not the same for all of them*, and the
difference is worth knowing before one is used to fix something urgently:

* `+content.store.max.object.size+` and `+content.store.local.fallback+` are
read on *every use*, so a row is in force at once, with no restart. They are
numbers and flags that the operation needing them consults; nothing is built
from either;
* every other `+content.store.*+` setting - the key prefix, the three
deadlines and the retry cap included - is *construction-bound*: it is sealed
into an SDK client, its credential provider or its override configuration when
the provider for a delegator scope is built, and none of those may be replaced
under requests already holding one. A change to one of these reaches only a
provider built afterwards, so *it needs a restart*. Changing one on a running
instance is reported once in the log, naming the scope and saying that a
restart is what applies it, rather than being applied.

`+content.store.s3.insecure.endpoint.allowed+` is read from the property file
alone, as every deployment-defining storage value is: it is the switch that
says "send these credentials unencrypted", the container entry point renders
and validates that file, and a row in a database table is not where that
decision belongs. The endpoint policy itself - scheme, instance metadata
addresses and the resolved addresses of the host - is enforced in Java
against whatever value arrives, from wherever.

They are all documented beside their values in
`+applications/content/config/content.properties+`, and the whole file is
rendered into `+/ofbiz/config/content.properties+` when any of the seven
variables above is set, so the defaults reach a configured container
unchanged.

Write such a row *through the framework* - the `+SystemProperty+` screens
in `+webtools+`, an entity-engine call, or an import through
`+webtools/control/EntityImport+` - and never with SQL against the
database. Each of these settings is read through
`+EntityUtilProperties+`, which resolves the row from the entity cache and
caches a *missing* row exactly as readily as a present one. Storing the
row through the framework clears that cache as part of the write; a direct
`+INSERT+` does not, so every instance goes on answering from the value it
resolved before the row existed - an override that appears to have been
applied and has not. Changing or removing a row has the same requirement.
A restart clears the cache too, which is the only reason a direct write
ever looks as though it worked.

*A `+SystemProperty+` row can override those tunables and nothing else.*
The eight settings that decide *where content goes and who it authenticates
as* - the provider, the bucket, the region, the endpoint, the two
credentials, the addressing style and the plaintext allowance below - are
read from the property file alone, never through the database. A deployment
whose start up validated an `+https+` endpoint and a specific bucket must
not have either replaced at runtime by a row in a table, because that row
is not subject to any of the validation above and is not visible in the
container's configuration at all: it would move content, or the identity it
is written with, without a trace in the deployment. The tunables above are
different in kind - each is a local performance or migration choice with no
bearing on which store is used - which is why they remain overridable.

One further setting is *derived* rather than supplied:
`+content.store.s3.insecure.endpoint.allowed+`. `+S3ContentStore+` refuses
an `+http://+` endpoint to any host but its own unless this permits it, and
the container renders it from `+OFBIZ_PROFILE+` - _true_ only for a
development profile that itself supplied an `+http://+` endpoint, and never
in _prod_, which refuses such an endpoint outright before the JVM starts.
It is re-derived on every start, so a container promoted from _dev_ to
_prod_, or simply moved to `+https+`, loses the permission with the change
rather than inheriting it from the override the previous start left on the
volume. A store on a loopback address needs no permission at all, which is
why a local MinIO beside the instance works with nothing set.

Values are validated before anything is written, so a mistake is reported
at start up rather than at the first upload an end user attempts:

* The provider is trimmed and folded to lower case, so `+S3+` and
`+ s3 +` select the object store. A value that is still not one of the
three names *aborts the start up*, naming the variable, the value and the
three accepted names. It does not fall back to `+database+`: which backend
holds durable content is not a decision an instance may make for itself,
and reading a mis-spelled selector as database storage would send every
upload to the instance's own writable layer - where the next replacement
destroys it - while both layers believed the configuration had been
honoured. `+ContentStoreFactory+` refuses the same value, so a container
that started anyway would fail at the first content read. Leaving the
variable unset, which is the unconfigured checkout, still means
`+database+`.
* `+OFBIZ_S3_BUCKET+` must satisfy the S3 bucket naming rules - 3 to 63
characters, lower case letters, digits, hyphens and dots, beginning and
ending with a letter or digit, no adjacent dots and not shaped like an
IPv4 address.
* `+OFBIZ_S3_REGION+` must look like a region identifier: 2 to 32
characters of lower case letters, digits and hyphens, beginning and
ending with a letter or a digit. The length is checked first and reported
as a length, so an endpoint pasted into this variable by mistake is named
as such.
* `+OFBIZ_S3_ENDPOINT+` must be an absolute `+http://+` or `+https://+`
URI with a host and without a query string, a fragment or embedded user
information. Credentials belong in the two credential variables, which
are rendered into a mode `+0600+` file, and are *forbidden* in the
endpoint - which is what refusing embedded user information, a query
string and a fragment enforces, each of those being a place a credential
is habitually smuggled. Because a URI can carry one anyway, no raw
endpoint value is echoed: the entry point suspends shell tracing around
the whole object-store region and reports an unused object-store setting
by variable *name* only, and `+S3ContentStore+` names the variable, or an
opaque reference, in a refusal rather than repeating the configured value.
Diagnose an endpoint problem from the variable that was named, not from
an endpoint printed in a log.
* `+OFBIZ_S3_ACCESS_KEY_ID+` and `+OFBIZ_S3_SECRET_ACCESS_KEY+` are
supplied together or not at all. Exactly one of the two aborts the start
up; neither of them selects the ambient AWS credential chain.
* An object-store setting supplied while the provider is *not* `+s3+`
aborts the start up in the _prod_ profile and warns in _dev_. The setting
would have no effect, and there is no way to guess from inside the
container which half of the contradiction was the mistake.

Two refusals are worth calling out, because they are about which identity
and which network the deployment ends up using.

*A credential pair is all or nothing.* `+OFBIZ_S3_ACCESS_KEY_ID+` and
`+OFBIZ_S3_SECRET_ACCESS_KEY+` are supplied together, and exactly one of
the two aborts the start up rather than falling back to the ambient AWS
credential chain. Falling back would mean a typo in one of the two
variable names, or a secret whose injection silently failed, changes
*which principal* the deployment authenticates as: from the credential the
operator supplied to whatever ambient identity the platform offers, which
on a cloud instance is usually a far more privileged role, and with no
error anywhere. Supplying neither is the deliberate way to ask for that
ambient identity.

*The instance metadata service is refused everywhere.* An endpoint that
points at `+169.254.169.254+`, `+[fd00:ec2::254]+`, `+169.254.170.2+` or
`+metadata.google.internal+` is refused in *every* profile, with no
variable that can relax it. The provider sends the deployment's own
credentials to whatever it is told is the object store, and the response
from that address is a set of role credentials for the whole instance.

That refusal is not a list match alone. `+S3ContentStore+` applies the
policy itself, in Java, against whatever endpoint reaches it - from the
entry point, from `+content.properties+` or from a `+SystemProperty+` row -
so the value's *source* stops mattering:

* the literal metadata addresses above are refused by name;
* the host is *resolved*, and every address it resolves to is inspected: a
  link-local, wildcard or multicast address is refused. So a perfectly
  ordinary-looking name that resolves to `+169.254.169.254+`, or to any other
  link-local address, is refused too. Loopback and private addresses are
  allowed, because that is what a store inside the deployment's own network
  looks like;
* a host that does not resolve at all is reported and accepted, so name
  resolution is not made a start-up dependency - but it is then treated as
  *not* loopback, which is the safe side of the next decision;
* `+https+` is *required* unless the endpoint resolves entirely to the
  loopback interface - a development store on the same machine, which cannot
  be observed off it - or `+content.store.s3.insecure.endpoint.allowed=true+`
  is set in the property file. Every object request carries this deployment's
  access key and secret, so plaintext means sending them across the network
  in the clear.

Two layers apply that last rule, and they are not identically strict, which
is worth knowing when a start up is refused:

* the *entry point* refuses `+OFBIZ_S3_ENDPOINT+` beginning `+http://+`
  outright in the _prod_ profile, with no loopback exception and no opt-in
  that reaches it - a deployed profile cannot be downgraded to plaintext by
  an environment variable - and warns about it in _dev_;
* the *provider* then applies the resolved-address policy above, in every
  profile. So a _dev_ container pointed at `+http://127.0.0.1:9000+` - the
  local MinIO case - works, while a _dev_ container pointed at
  `+http://minio.example.internal:9000+` is refused when the provider is
  built unless the property-file opt-in is set.

The practical reading: use `+https+`, or loopback, or state the opt-in
deliberately. A mistake in the endpoint's *shape* is reported at start up
rather than at the first content operation.

Withdrawing the configuration undoes it. `+/ofbiz/config+` is a volume that
outlives the container, so when no object-store variable is set the
container *removes* an override an earlier start rendered rather than
leaving it in force - which is what makes withdrawing the variables return
the instance to the committed database storage instead of leaving object
storage quietly in effect.

The provider handles content *bytes* only. The `+DataResource+` entity, the
Content component's service signatures and the `+objectInfo+` values
persisted in the database are unchanged by the choice of backend, so
nothing in the data model records which store a document went to. That is
also why a switch moves nothing: content written before one stays where it
was written, and `+content.store.local.fallback+` is the bridge that lets a
fleet be switched to `+s3+` before every existing object has been copied
into the bucket. See _How content reaches and leaves the object store_
below.

===== How content reaches and leaves the object store

The provider serves *reads and writes* of file-backed content, which is what
makes an instance replaceable: an upload does not land on the instance that
accepted it. The bytes go to the provider every instance of the deployment
reaches, under the key both read paths derive for the same resource, so the
content is servable by any instance and survives the one that received it.

The write goes through the same seam the reads do, in
`+applications/content/src/main/java/org/apache/ofbiz/content/data/DataResourceWorker.java+`,
and it changes no service signature, no service definition and no entity
definition. Fifteen things follow that are worth knowing when you operate a
fleet.

*Four operations reach the store.* Rendering text content into a screen or
a template, and streaming binary content to a browser, read the object from
the bucket every time - so an instance never serves a version another
instance has replaced, and it never depends on a file only it holds.
Resolving a content location for a caller that needs a real file
reconstructs that file from the bucket when this instance has no copy of it.
And a transaction that *commits* having changed content under a resolved
location publishes it, or removes it from the bucket when it removed the
file. Nothing else in the running system contacts the store; in particular,
removing a `+DataResource+` row does not, for the reason given below.

*Publication is bounded by `+content.store.max.object.size+`; a read that
streams is not.* The ceiling - 10 MiB by default - bounds what one
whole-object operation may hold in memory, which is the read a caller uses
when it knows the content is modest, and what one write may publish. The
bound is applied to the *file the transaction produced*, immediately before
that transaction commits, so it covers every way content reaches disk - a
streamed upload and a byte-array service write alike - and it is enforced by
*rolling the transaction back*: neither the `+DataResource+` row nor the
object is kept, so nothing is left half stored and nothing is recorded that
no consumer could then be served in one piece. Raise the setting in a
deployment that stores content this large. The two reads a
running instance performs are *streams* and are deliberately outside the
bound, as the item on what a read leaves behind sets out below, so the
ceiling does not have to be sized against the largest binary resource the
deployment serves, and a
read the local fallback answers is the same local stream the deployment
performed before the store was configured. Every refusal the ceiling
produces, from either backend, names the ceiling and a correlation
reference and nothing else: the path, the size and the key go to the log
under that same reference, so a refusal can be diagnosed from the log
without the page disclosing where the deployment keeps its content.

*What is published is what the upload validation left behind - and this
follows from where the publish happens rather than from a check of its own.*
The services that write `+DataResource+` content are OFBiz's own and are not
modified by this image. `+createFile+` and its relatives write the submitted
bytes to a *temporary* file, hand that file to OFBiz's `+SecuredUpload+`
validation - which for an image decodes it and REWRITES it, stripping the
metadata with it - and copy the result onto the target. So the file on disk
holds post-validation content, and the publish, which happens at commit and
reads *that file*, can only carry post-validation bytes. Nothing the
validation refused reaches a store every instance can read either, because a
refused upload returns a service error, the transaction rolls back, and a
transaction that does not commit publishes nothing. The service signatures,
the `+DataResource+` entity and the `+objectInfo+` values are unchanged: the
routing happens underneath them.

*A publish happens when the transaction that recorded the content commits -
never before it, and never at all if it does not.* Resolving a content
location inside an active transaction registers the work; what that work
publishes is decided by comparing the location against what it held when it
was resolved, and it is carried out only on a `+COMMITTED+` completion.
Three consequences are worth stating, because each of them was a way to lose
content:

* *a rollback publishes nothing and removes nothing.* Whatever the bucket
already held - including a version another transaction committed in the
meantime - is left exactly as it was. A failed write cannot delete the
object a previous, successful write put there;
* *nothing is ever visible in the bucket for a row that was not committed*,
because the object is written after the commit rather than before it;
* *a resolution that only reads publishes nothing*, because the location is
unchanged when the comparison is made. That is what lets one seam serve
reads and writes without having to be told which it is serving.

A resolution made *outside* an active transaction registers nothing, and is
reported once per location rather than once per read - every service runs in
a transaction, so that report means a write path that does not, and content
written through it stays local to the instance that wrote it. Should the
publish itself fail after the commit, the object is not in the bucket, the
key is named in an error line, and it has to be published by hand: the row
is already committed, so there is nothing left to roll back.

*The `+filesystem+` provider publishes nothing, because the write already
reached it.* Its storage tree *is* the deployment's own tree and its keys
are the deployment's own paths, so a service that wrote a file under
`+/ofbiz+` has by construction written it into that provider, and handing
the same bytes over again would only rewrite the file it just wrote. That
is also why that provider makes a fleet stateless only if every instance
mounts the same tree. Database storage needs no publication either: the
bytes are in the `+DataResource+` columns and are shared the moment the row
commits.

*An object is addressed by the content's own path, and by the same path for
every provider.* Under the configured `+content.store.s3.key.prefix+`, the
key is the content's location relative to `+/ofbiz+` - so a resource whose
`+objectInfo+` resolves to `+/ofbiz/runtime/uploads/1699/10000.png+` is the
object `+runtime/uploads/1699/10000.png+`. That is exactly the key the
`+filesystem+` provider uses, which is the point: one derivation for both
providers is what makes them interchangeable, so content published through
one can be read through the other and a deployment can move between them
without rewriting a single key. It is also the only value both of the
resolution seams always have - one of them resolves an upload *directory*
before the row that will name the file exists - so it is the only derivation
that can serve them both.

Every key is held to one grammar, whichever provider is active and whichever
seam derived it: `+/+`-separated, no leading separator, no `+.+` or `+..+`
component, no control character, and bounded per component and as a whole by
what an object store and a filesystem both accept. A key that would reach
outside the configured prefix, or outside the provider's own tree, is
refused rather than resolved somewhere else.

*The key carries no deployment identifier, so separate deployments need
separate namespaces - and so do separate tenancies that share paths.* Two
independent deployments both write `+runtime/uploads/...+`, so a path
occurring in both names one object for both and whichever published last is
what both then read. Give each deployment a distinct
`+content.store.s3.key.prefix+`, or a bucket of its own, before letting two
of them share a store; the committed prefix is empty, so this is a
configuration you have to supply.

Tenancies work the same way, and the same way they already work *on disk*: a
tenanted delegator that resolves the same upload path as another tenancy
writes the same local file too, so the store gives a fleet precisely the
separation the deployment already has. Where tenant content has to be kept
apart, keep it apart where OFBiz already provides for it - give each tenancy
its own `+content.upload.path.prefix+` through a `+SystemProperty+` row,
which the upload path resolution reads *through the delegator* - and the keys
follow. One `+DataResource+` row means one object, whichever delegator reads
it.

*Some content is never provider-backed and is always read from, and written
to, local disk.* Three exclusions, and they are the whole of the rule; each
applies to reads and writes alike, so no resource can be written to one
backend and read from another:

* a location *outside* `+/ofbiz+` - an absolute `+LOCAL_FILE+` elsewhere on
the host - is host-local state an operator placed deliberately, and no key
describes it;
* a *relative* location is refused by the resource type itself, so it never
reaches a provider;
* `+CONTEXT_FILE+` and `+CONTEXT_FILE_BIN+` content ships inside the image
and is byte-identical on every instance, so there is no durable local state
to externalise - and making it provider-backed would instead require every
instance's own static files to be uploaded before it could serve them. Both
types are excluded, on the rendering path and on the binary streaming path
equally, so the bucket never has to hold a webapp's static files.

*Content that predates the switch is yours to copy in once.* Publication
applies to writes made while the store is configured; it cannot reach back
to the shipped demo content, to a `+DataResource+` whose file was uploaded
before the store existed, or to anything an earlier `+filesystem+`
deployment left in `+runtime/uploads+`. Copy those objects into the bucket
once, at the key described above, and the fleet reads them from there
afterwards. Because the key *is* the `+/ofbiz+`-relative path, the copy is a
path-for-path upload and needs no lookup to derive a name:

[source,shell script]
----
# Whatever content.store.s3.key.prefix is set to, empty if it is unset. It has no
# environment variable of its own, so this is a variable of this script alone:
KEY_PREFIX=

# The paths a DataResource row can name. Read them from the database rather than
# walking the tree, so that only content the application references is copied:
PGPASSWORD="$OFBIZ_POSTGRES_OFBIZ_PASSWORD" psql -h "$OFBIZ_POSTGRES_HOST" \
    -U "$OFBIZ_POSTGRES_OFBIZ_USER" -d "$OFBIZ_POSTGRES_OFBIZ_DB" -At -c \
  "select object_info from data_resource
     where data_resource_type_id in
       ('OFBIZ_FILE', 'OFBIZ_FILE_BIN', 'LOCAL_FILE', 'LOCAL_FILE_BIN')" \
| while read -r path; do
    # OFBIZ_FILE paths are relative to /ofbiz; LOCAL_FILE paths are absolute.
    case "$path" in /ofbiz/*) file="$path" ;; *) file="/ofbiz/${path#/}" ;; esac
    [ -f "$file" ] || continue
    # The key is the same path with /ofbiz/ removed - nothing else is derived.
    key="${file#/ofbiz/}"
    aws s3 cp "$file" "s3://$OFBIZ_S3_BUCKET/${KEY_PREFIX:+$KEY_PREFIX/}$key"
  done
----

A `+LOCAL_FILE+` outside `+/ofbiz+` is skipped by the `+case+` above turning
it into a path under `+/ofbiz+` that does not exist - which is correct, since
such a location is never provider-backed. Run this from a host that can read
the upload tree - a job container with the same `+/ofbiz/runtime+` volume,
for instance. Leave
`+content.store.local.fallback+` at its committed _true_ while the copy is
in progress: content the bucket does not hold yet keeps serving from the
local file, and each such resource is named once in the log so you can see
what is left. Set it to _false_ once the copy is complete, which is the
strict posture in which the bucket is the only authority. Until content is
in the bucket, only the instance that holds a copy of it can read it -
which is the state the `+filesystem+` provider leaves a fleet in
permanently.

*The bucket always wins where it holds content; a local copy only fills
gaps.* Where the bucket holds an object for a resource, that object is what
every instance serves, whatever any instance happens to have on disk - so
one instance can never quietly return content another has replaced. Where
the bucket holds nothing and this instance does hold a file at the recorded
path, `+content.store.local.fallback+` decides:

* _true_, the committed default, serves the local copy and names the
resource in the log once - not once per read - so switching a running
deployment to `+s3+` never stops it serving content it served the day
before, and the log tells you what has yet to be copied in.
* _false_ refuses the read with an error naming the setting. That is the
strict posture to run once the copy above is complete: the bucket is
the only authority, and a file only one fleet member can see is an error
rather than an answer. Selecting `+s3+` while it is _false_ logs a warning
at start up naming exactly what will be refused, so the posture is never
adopted by accident.

Content that exists neither in the bucket nor on disk is reported as absent
exactly as it always was.

*The two reads that serve a consumer write nothing and leave nothing
behind.* No staging file, no spool file and no local cache of a fetched
object. Neither materialises the object: rendering text content copies the
provider's stream into the output as it arrives, and streaming binary content
to a browser hands its consumer the provider's own stream together with the
length the store reported for it. That is why
`+content.store.max.object.size+` does not apply to either of them - the
bound exists to stop one whole-object read exhausting the heap, and a stream
never holds the object at all, so content of a size an uploader chose is
served in full rather than refused for being large.

*The one read that must answer with a `+File+` reconstructs it, at the
content's own path.* Some callers - the binary content services, and report
templates that dereference a file - are owed a real `+File+` rather than a
stream, and on an instance that never received the upload there is nothing
at that path. Rather than fail, or hand back a temporary copy that a caller
about to WRITE would write into and lose, the content is written back to the
location the row names: staged in the same directory and moved onto the
destination atomically, so a concurrent reader sees either nothing or the
whole value. The location is authorised - by the same allow list that
resource type always applied - *before* anything is created, and a location
with no key is never reconstructed. The effect is that the local tree becomes
a read-through cache of the bucket: nothing on an instance is durable state,
because any instance can rebuild it from the store, and a writer's write is
never sent anywhere except the file it was always going to write. This
reconstruction streams the object onto disk rather than holding it, so it is
outside the whole-read ceiling as well. So there is nothing for a rolled-back
transaction to leave stranded on a read, nothing for an operator to clean up,
and no durable local state that another instance could not rebuild - which is
what makes an instance freely replaceable.

*Deleting a `+DataResource+` row does not delete the object.* Removing the
row removes the row and nothing else, exactly as it always has:
`+removeDataResource+` is a plain entity delete, OFBiz has never deleted the
file a file-backed resource named, and this image does not change that -
doing so would alter the behaviour of a service rather than the storage
underneath it, and it would make the object store *lose* content that the
`+filesystem+` provider keeps.

*The one removal the store performs follows the file.* When a transaction
that resolved a content location commits having *removed the file*, the
object is removed too, so the bucket does not go on serving content the
deployment has discarded. That is the whole of the deletion policy: the store
follows the file, and nothing else. So a row deleted without its file leaves
the object, exactly as it leaves the file. Objects therefore accumulate, and
an object nobody references is still an object somebody can read - so decide
how they are reclaimed before treating the bucket as a compliance boundary.

*Reconcile against the `+/ofbiz+`-relative paths of the rows, under every
prefix the bucket holds.* This is the one piece of housekeeping that can
destroy live content if it is written from the wrong premise, so it is worth
being exact about. The live key set is derivable without contacting anything:
for every `+DataResource+` row of a file-backed type, resolve `+objectInfo+`
the way the application does - relative to `+/ofbiz+` for the `+OFBIZ_FILE+`
types, absolute for the `+LOCAL_FILE+` ones - drop the `+/ofbiz/+` prefix,
and prepend the configured `+content.store.s3.key.prefix+`. Skip any location
that does not lie under `+/ofbiz+`, and skip the `+CONTEXT_FILE+` types
entirely: neither is ever provider-backed, so neither has a key to keep.

A bucket shared by several deployments holds one such namespace per prefix,
and every one of them has to be enumerated before anything is called
orphaned; a reconciliation that knows about only some of them will condemn
the rest. If a deployment shares a bucket with *no* prefix configured, do not
reconcile it at all until one is - there is no way to tell whose content an
object is.

Then treat what it produces as a proposal rather than a verdict:

* *Dry run first.* Report the keys the job *would* delete, with a total and
  a sample, and delete nothing on that pass. Compare the total against the
  bucket's own; a proposal naming most of the bucket is a defect in the job,
  not a backlog of orphans.
* *Require explicit review.* Acting on a reported set should be a separate,
  deliberate action, so that no schedule can delete on its own.
* *Keep a grace period, and keep versioning on.* Consider only objects
  whose last modification is older than the longest window in which a row
  and its object may legitimately be out of step. That window is short - a
  publish happens as the recording transaction commits - but it is not zero:
  a row commits an instant before its object is written, content placed in
  the bucket by the copy described above can exist before its row does, and a
  publish that failed after its commit leaves a row with no object until an
  operator publishes it. Enable bucket versioning, or a
  lifecycle rule that moves a deletion into a quarantine prefix rather than
  removing it, so that a mistaken deletion is recoverable.
* *Prefer expiry to reconciliation where it fits.* A lifecycle rule on a
  prefix that only ever holds transient content needs none of the above. Do
  not point one at a prefix holding live content: a lifecycle rule has no
  way to know which objects are referenced.

=== Examples of running the OFBiz container

[source,shell script]
docker run -it -e OFBIZ_PROFILE=dev -p 8443:8443 ofbiz-docker


Launch the OFBiz container, load the seed data, create the administrator
user with name `+admin+` and password `+ofbiz+`, listen on port 8443 for
connections to `+localhost+`.

Users can access OFBiz at https://localhost:8443/partymgr

The docker container will remain attached to the terminal. Interrupting the
container, i.e. pressing Ctrl-C, will trigger a graceful shutdown of the
container.

[source,shell script]
docker run -it -e OFBIZ_PROFILE=dev -e OFBIZ_DATA_LOAD=demo -p 8443:8443 ofbiz-docker

Launch the OFBiz container, load the demo data, listen on port 8443 for
connections to `+localhost+`.

The demo data includes the administrator user with name `+admin+` and
password `+ofbiz+`.

[source,shell script]
docker run -it -e OFBIZ_PROFILE=dev -e OFBIZ_DATA_LOAD=seed -e OFBIZ_ADMIN_USER=localadmin -e OFBIZ_ADMIN_PASSWORD=TTTTT -p 8443:8443 ofbiz-docker


Launch the OFBiz container, load the seed data, create the administrator
user with name `+localadmin+` and password `+TTTTT+`, listen on port
8443 for connections to `+localhost+`.

[source,shell script]
docker run -it -e OFBIZ_PROFILE=dev -v 'C:\ofbiz-framework\add-data':/docker-entrypoint-hooks/additional-data.d -p 8443:8443 ofbiz-docker
